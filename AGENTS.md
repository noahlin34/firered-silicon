# AGENTS.md — Pokémon FireRed Native Apple Silicon Port

## 1. Project Overview
This repository is based on **pokefirered** (the pret decompilation of *Pokémon FireRed* for the Game Boy Advance).
- **Core Architecture:** 32-bit GBA C engine originally targeting the ARM7TDMI processor.
- **Primary Mission:** Port the game to run **natively as a 64-bit Mach-O ARM64 executable on macOS (Apple Silicon)** using **SDL2**, without requiring an external GBA emulator or GBA cross-compilation toolchains.

---

## 2. Key Technical Decisions & Constraints

### The 64-Bit Apple Silicon Reality
1. **No 32-bit binaries:** macOS on Apple Silicon (arm64) does not support 32-bit binaries or 32-bit ARM assembly (`armv4t`/`arm7tdmi`). Any inline assembly or `.s` files targeting GBA registers/instructions must be guarded with `#ifndef PORTABLE` or replaced with portable C.
2. **Memory Virtualization:** GBA physical addresses (`0x04000000` I/O registers, `0x05000000` Palette RAM, `0x06000000` VRAM, `0x07000000` OAM, `0x0E000000` Flash) cause segfaults if dereferenced directly on macOS. They are abstracted via `#ifdef PORTABLE` to point to host-allocated global buffers (`REG_BASE`, `PLTT_`, `VRAM_`, `OAM_`, `FLASH_BASE_`) in `src/platform/system.c`.
3. **No DMA pointer truncation:** GBA register-based DMA writes (`DmaSet`) cast source and destination addresses to 32-bit integers. On 64-bit systems, this truncates 64-bit pointers. In `include/gba/macro.h`, `DMA_COPY` and `DMA_FILL` are implemented as synchronous memory copy/fill functions under `PORTABLE`.
4. **Software GBA PPU:** The GBA engine does not write to a linear framebuffer; it writes tiles, tilemaps, and OAM structures. A software PPU (`src/platform/ppu.c`) composites Mode 0/1 background layers and 128 OAM sprites into a 240×160 15-bit BGR555 texture displayed via SDL2 at the GBA's approximately 59.7275 FPS.

- [x] **Software PPU Compositor (`src/platform/ppu.c`, `include/platform/ppu.h`):**
  - Scanline compositor for Mode 0 text backgrounds ($32\times32$, $64\times32$, $32\times64$, $64\times64$ tilemaps with 4bpp/8bpp tiles, flipping, and scrolling).
  - 128 OAM sprite compositor with transparency, priority sorting, and 4bpp/8bpp palettes.
  - **Affine (rotated/scaled) OAM sprites.** The sprite path computes an inverse affine transform per pixel from `gOamMatrices[oam.matrixNum]`, so the Poké Ball spins while the player throws it and the ball send-out's battler scale/shrink actually samples. Double-size (`affineMode >> 1 & 1`) sprites map their tile block against the *undoubled* object dimensions while covering a doubled bounding box, matching hardware. Before this the matrices were computed but never read — the ball flew without spinning.
  - **Display windows (WIN0/WIN1/OBJWIN).** `ComputeWindowMask()` classifies each pixel by region (priority WIN0 > WIN1 > OBJWIN > outside) and derives the region's effective layer enables from `REG_WININ`/`REG_WINOUT`. Masking is active only while a window is switched on in `REG_DISPCNT`; otherwise the ordinary layer enables apply everywhere. The window's colour-effect bit gates `REG_BLDY`/blend per pixel, and an OBJ-window sprite is not drawn — its opaque pixels only mark the region. This is what the OPTION menu's cursor-row highlight and the battle-transition wipes are built from.
  - **Per-scanline HBlank DMA.** `DmaSet` records HBlank-timed channels (`PortableDmaSet`, `src/platform/system.c`) and `Platform_RunHBlankDma()` replays one transfer per rendered scanline, so per-scanline effects that feed `REG_WIN0H`/`REG_BLDY`/`REG_BGxHOFS` through DMA work. Immediate (`DMA_START_NOW`) transfers still run inline.
  - Alpha blending (`REG_BLDCNT`, `REG_BLDALPHA`) and brightness increase/decrease (`REG_BLDY`).
  - Mode 1 affine BG2 compositor renders Oak's scrolling/zooming backdrop and trainer portraits; verified through Oak and the selected player portrait.

- [x] **Sound: the m4a driver runs natively and the game is audible (`tools/gen_sound_data.py`, `src/m4a_driver.c`, `src/data/sound/*`, `src/platform/sdl2.c`):**
  - **The game was silent, and the reason was structural.** `src/m4a.c` was already portable C, but it holds only the *public API* (song start/stop, fades, `MidiKeyToFreq`, the CGB square/noise synthesiser) — the **sequence interpreter and the PCM mixer live in GBA assembly** in `src/m4a_1.s` (~30 functions: `SoundMain`/`SoundMainRAM`, `MPlayMain`, `ply_note` and the 25 `ply_*` handlers, `TrackStop`, `RealClearChain`, `ChnVolSetAsm`, `m4aSoundVSync`). None of it could be built for arm64, and `src/platform/stubs.c` defined the entire high-level sound layer (`PlayBGM`, `PlaySE`, `InitMapMusic`, `m4aSoundMain`, …) as empty functions.
  - **The PSG (CGB) half of the hardware was missing, and it is the bigger half.** The GBA's sound hardware is two independent sources: the DirectSound FIFOs the PCM mixer fills, and four PSG channels (pulse 1, pulse 2, wave, noise). `CgbSound()` (`src/m4a.c`) computes every CGB channel's envelope, period and duty each vblank and writes them to the `NR10`..`NR52` registers — **on hardware those registers are the oscillators**, so the engine is complete and correct. Under `PORTABLE` they were written into `REG_BASE` (plain host memory) and never read, so all four channels were silent. That is not a corner case: FireRed's voicegroups are built on CGB voices, and measuring the live engine showed the title theme driving pulse 1 and pulse 2 alongside its four DirectSound tracks (registers 1714 and 1650, i.e. G4 and E4 — exact pitches, which is what confirmed the frequency formula), Pallet Town driving two CGB squares of its six tracks, and `mus_lavender`, `mus_pewter`, `mus_sevii_123`, `mus_poke_tower` and `mus_vs_deoxys` all using CGB voices. The port was mixing the accompaniment and dropping the melody and bass — which is what "low fidelity" sounds like. `src/platform/psg.c` synthesises them from the registers the engine already wrote (the same split the PPU uses for the video registers), and adds the result into the same two PCM halves the DirectSound mixer fills, saturating rather than wrapping because the DAC sums both sources in the analogue domain.
  - **Two things about the PSG model are non-obvious and were both wrong on the first attempt.** (a) **The channel level cannot be read from NRx2.** Its high nibble is the envelope's *initial* volume and its low nibble instructs the hardware envelope unit; the engine writes 0 there when a note attacks from silence and keeps the running level in `CgbChannel.envelopeVolume` (measured on a live note: NRx2 read `0x09`, initial volume 0, while the engine's envelope climbed 0,1,2,3,4). Reading the register gave a permanent zero. The level therefore comes from the engine's `envelopeVolume`, falling back to the register so the synthesiser stays a pure function of the registers when a caller has not set up CGB state. (b) **The 4-bit scale must be scaled to the PCM byte.** A CGB level is 0-15, so centring it and dividing by the duty puts envelope 1 at +/-0.5 and rounds *every* sample to zero; the music uses envelope 1-4, so the synthesiser was computing the right waveform and emitting nothing. `PSG_DAC_SCALE` (8) puts a full-envelope channel at +/-60 of the 8-bit range and keeps envelope 1 at +/-4.
  - **No off-the-shelf C port existed at this level.** poryaaaa drives the mixer from MIDI rather than song bytecode (a different input path, not a drop-in), agbplay is C++, and pret's `modern` branch has no m4a C rewrite. The driver was therefore transcribed from `src/m4a_1.s` into `src/m4a_driver.c`, function for function, keeping the assembler's exact arithmetic — the mixer's 8-bit output, its 23-bit interpolation fraction and the reverb feedback all depend on exact bit behaviour, and a "cleaned up" mixer is audibly different and silent in the wrong places.
  - **`tools/gen_sound_data.py` compiles the audio data**, the counterpart of `gen_map_data.py`/`gen_battle_data.py`. It reads pret's own sources and emits host-shaped C into `src/data/sound/{voice_data.h,song_data.h,sound_data.c}` (tracked in git, like the other generated headers): 77 voicegroups, 5 keysplit tables, 11 programmable waves, 477 sample blobs, 347 songs, 776 cry entries. **Every song bytecode pointer operand is a u32 index into `gNativeSongPtrs`** rather than an address (fix #23's treatment), because a 4-byte operand cannot hold a 64-bit pointer. `mid2agb`/`wav2agb` already built natively; `Makefile.native` gained the wav2agb rules (cries are DPCM-compressed and padded to 4 bytes, voices are not) and `tools/list_incbin_assets.py` learned that `.bin`-from-`.wav` targets are real, so its report no longer flags all 477 samples as unbuildable.
  - **A voicegroup's keysplit pointer gets its own field.** `voice_keysplit`/`voice_keysplit_all` store a keysplit table pointer in what the GBA layout calls `attack`/`decay`/`sustain`/`release` — four bytes, enough for a GBA address and half a host one. `struct ToneData` therefore gained a PORTABLE-only `keySplitTable` field and the generator emits that instead of the aliased bytes.
  - **The platform drains the PCM buffer** the DMA would have fed. The driver mixes one vblank into `SoundInfo.pcmBuffer` as two mono halves (FIFO A = right at the start, FIFO B = left at `+ PCM_DMA_BUF_SIZE`); `Platform_SubmitAudioFrame()` hands those to an SDL audio device opened at 48 kHz, with the engine's ~13.4 kHz stream resampled by nearest neighbour and a frame queue absorbing the difference between the engine's 59.7275 Hz clock and the device's rate. It is called from `VBlankIntr` **after** `m4aSoundMain()`, so the buffer it ships is this vblank's mix and not the previous one's — **this call site is the thing that makes the game audible, and it was missing**: the driver mixed correctly, the song sequenced and the device opened, but nothing ever handed the buffer over, so a port that looked wired end to end was silent (fix #71).
  - **Three driver bugs found on the way, all silent by construction** (the game ran fine and made no sound):
    1. **`ply_note` writes four channel bytes with one word store.** `ldr r0, [track, o_MusicPlayerTrack_gateTime]; str r0, [chan, o_SoundChannel_gateTime]` copies `gateTime/key/velocity/runningStatus` onto `gateTime/midiKey/velocity/priority` at once. Spelling out `gateTime` alone leaves `velocity` at 0, and `velocity` is what `ChnVolSetAsm` scales the channel volume by, so every PCM channel mixed silence.
    2. **The envelope stage scales by `masterVolume`, read through the wrong offset.** `[sp,0x18]` holds the *SoundInfo* pointer, so `ldrb r0, [r0, o_SoundChannel_release]` (`SoundInfo + 7`) lands on `masterVolume`, not on a channel's release byte. Using the channel field scales the output down 16-fold — inaudible, not silent, which is harder to spot.
    3. **A track's blocks must stay contiguous.** mid2agb emits a track as a sequence of labels (`mus_x_1`, `mus_x_1_B1`, …) and the interpreter *runs off the end of one into the next*. Emitting each label as its own array made that continuation depend on linker placement, so `mus_pallet_1` (2 bytes, `KEYSH 0`) fell into unrelated rodata instead of its first block. Each track is now one array with its labels as offsets, which is what the assembler's layout means. **This one only reproduced inside the test binary** — the game binary happened to place the arrays favourably — which is exactly why the tests exist.
  - **Two latent port bugs surfaced once the sound functions stopped being stubs:**
    - **`REG_KEYINPUT` powers up reading "every button held".** It is active low, so the zeroed `REG_BASE` meant the engine's soft-reset check (A + B + START + SELECT) fired on the very first `ReadKeys()` — before `Platform_UpdateInput` writes the real SDL state from the frame loop. Previously `DoSoftReset`'s calls were all stubs and nothing happened; now its `m4aSoundVSyncOff()` leaves the sound system disabled for the rest of the session (`ident` parked at `ID_NUMBER + 10`). `REG_BASE` is seeded via a designated initializer and `RegisterRamReset` restores the same value.
    - **`IsPokemonCryPlaying(NULL)` is a crash on the host.** `RestoreBGMVolumeAfterPokemonCry` creates the ducking task unconditionally, so it can ask whether a cry is playing while `gMPlay_PokemonCry` is still NULL. On the GBA, dereferencing address 0 read the BIOS and returned garbage the `&&` discarded; here address 0 is unmapped and the battle's task loop faulted (fix #64's class). `IsPokemonCryPlaying` now returns FALSE for a NULL player.
  - **The resampler between the engine and the device was the cause of the "choppy" sound, and it had three defects.** The engine produces 8-bit PCM at 13,379 Hz (224 samples per vblank at 59.7275 Hz); the device runs at 48 kHz. Bridging those rates is `src/platform/audio_resample.c` (extracted from `sdl2.c` so it can be tested -- the test binary has no SDL and excludes `sdl2.o`). What it replaced was wrong in a way that was audible and measurable:
    1. **It was a zero-order hold, not interpolation.** Nearest-neighbour repeats each engine sample 3.6 times, and that step train puts the source band's images back into the audible range: measured on a real run's buffer, **2.27% of the output's energy sat above the source Nyquist with its largest image at 11.9 kHz from a ~1.5 kHz tone** -- a whistle the game never contained and no emulator produces. There was a comment defending this as "not inventing detail", which was backwards: the hardware's own reconstruction is a continuous DAC output with far better anti-imaging than either choice, so the hold was the option adding artefacts. Linear interpolation takes it to **0.12% modelled / 0.36% measured in the shipped binary**.
    2. **Interpolating in 8-bit sample units rounds the blend away.** One 8-bit step is large next to a single output frame: engine samples are 48000/13379 = 3.59 frames apart, so the blend fraction never exceeds 0.84 and a delta of 1 or 2 sample units truncates to zero for every frame in the interval. Done in sample units the "interpolation" therefore degenerates to the hold for exactly the small deltas that make up most of a quiet passage -- it measured 0.43% instead of 0.12% until the delta was shifted into the output's scale (and the product widened to 64-bit, since 255 << 8 times 48000 overflows `s32`).
    3. **The sub-sample position must be carried between vblanks.** Position 0 of the next vblank is the same instant as position `n` of this one, so the leftover resumes exactly where the last call stopped. Each vblank is 803.6475 output frames, and restarting the position per vblank throws that 0.6475 away every time: **176 frames of drift per 500 vblanks (~0.04%)**, which accumulates into a slow pitch rise against the DirectSound layers still playing in tune. This one is invisible to a waveform check -- the error is in timing, not amplitude, so the output stays perfectly smooth while playing at the wrong rate.
  - **The PSG channels also had to be summed before being clamped, not clamped individually.** `Platform_PsgMix` adds four CGB channels, and clamping each one and then adding the results is not the same as adding them and clamping once: the sum of four already-clamped values is still far outside the byte, so a loud vblank produced a squared-off plateau instead of the single clip the hardware makes (its DAC sums the channel currents and clips the total). The four channels now accumulate into `s32` scratch and are clamped once, then summed onto the DirectSound mix with saturation. Measured, this was not the audible symptom -- the PSG total peaks at only +/-21 here -- but it is what the hardware does, and the per-channel form was a latent defect for any louder song.
  - **The queue underruns only at startup; steady-state audio never starves.** Instrumenting the SDL callback (`played`/`under`, and underruns counted only after the 50th callback) showed 0 late underruns over 400 frames: every one of the ~1% raw underruns is in the first few callbacks while the queue primes. Chasing "choppy" through buffer sizing would have been wasted; the seam statistics and the spectrum are what located the actual defects.
  - **The notes hold for their real duration (fix #75).** `ply_note` was copying only the voice's `attack` byte to the channel, leaving `decay`/`sustain`/`release` (and `pseudoEchoLength`) at 0. The envelope state machine's decay stage then computed `volume = (volume * 0) >> 8 = 0`, found it at the sustain of 0, and switched the channel off — so every note died the vblank after its attack ramp finished (~5 vblanks at attack 51 of 255). Measured on Route 1, **25.8% of output frames were exact digital silence across 1,581 dropouts**, which is the stutter and the buzz; after the fix it is **2.1%**, with RMS 828 → 2167 and peak 9958 → 25533 (nothing at the rail). The assembler does both copies with wide stores over adjacent fields (`str r0, [chan, o_SoundChannel_attack]` carries all four envelope bytes, `strh r0, [chan, o_SoundChannel_pseudoEchoVolume]` carries the echo pair), which is why field-by-field transcription missed them.
- **Pinned by `tests/sound.c`** (14 tests; the four PSG ones are described under the "PSG (CGB) channels" heading in that file, the three resampler ones below theirs, and `a channel carries the voice's decay, sustain and release` asserts fix #75's relationship — an ON PCM channel must have at least one of decay/sustain/release non-zero, since a real voice never has all three at 0 — so it fails on the historic defect without pinning a literal). The driver boots: `ident`, `plynote`, `MPlayMainHead` and `CgbSound` are all live. The **handoff** is asserted too (`the engine hands its mix to the platform every vblank`, via the harness's recording of the real `VBlankIntr` call site — the driver mixing and the mix *reaching the platform* are different claims and only the second one is audible; see fix #71), as is the both-halves clear (`each vblank clears both PCM halves before mixing`, fix #72). Playing `MUS_PALLET` through the real `PlayBGM` sequencers it (the first track consumes commands; the player's status low half is a per-track alive mask) **and mixes non-silent audio** — the buffer the platform hands to SDL is non-zero, which is the assertion that fails when the velocity or master-volume bugs return. A second test asserts a live channel's `velocity` and per-side volumes are non-zero and that `envelopeVolume{Left,Right}` equal the master-volume formula, so a reintroduced 16-fold scaling error fails on the value rather than on audibility. Two pure tests cover the generated tables (a GOTO operand resolves to real bytecode, `voicegroup000` is the ROM's, keysplit voices carry their table pointer, `gCryTable[0]` points at a sample).
  - **The harness runs the real frame loop, and records the audio handoff.** `firered-tests` substitutes only `src/platform/{sdl2,dev_panel,main}.c`, so `src/main.c`'s `WaitForVBlank` → `VBlankIntr` (and therefore the handoff call site, fix #71) runs once per frame exactly as in the game. The harness's `Platform_SubmitAudioFrame` has no device to play on, so it **counts the submits and accumulates their magnitude** into `gHarnessAudioSubmits`/`gHarnessAudioMagnitude` (`tests/platform_host.c`, declared in `tests/registry.h`); `sound/the engine hands its mix to the platform every vblank` asserts through those. Tests that want the driver's own contract (one vblank of mixing under their control) still call `m4aSoundVSync` + `m4aSoundMain` themselves and read `gSoundInfo.pcmBuffer`.
  - **Verified:** all 347 songs and 477 samples compile; the game boots at 59.7275 Hz with a 48 kHz stereo device open, and `./firered-tests` passes 82/82. The resampler's three tests each fail on their own defect and only their own (verified by restoring the hold: `repeats <= 3` and the roughness margin both fail; by resetting the sub-sample position: the output-count test fails while the other two pass). PSG measured on the real binary by disabling the `SoundMain` call site and diffing the audio the SDL callback played: on the title theme the CGB layers carry **32.9% of the mix energy** (RMS 1126 -> 1193, peak 5888 of 32768, 9.4% of samples changed) with no added clipping. The bedroom contributes 0 at the sampled moments because the engine has genuinely stopped those channels there (`cgbChans[].statusFlags == 0`, `envelopeVolume == 0`, NR51 routing only channel 1) — the gate is the engine's, not the synthesiser's. **This entry originally claimed the port was audible when it was not** — the handoff call site was missing (fix #71), so the acceptance test was a person listening, not a green suite. Measured on the fixed binary with a temporary probe: 400 vblanks produced 400 submits totalling 89,600 engine samples (400x224, exactly one per frame) with the SDL queue draining and both channels non-silent. Both driver regressions were confirmed to fail the new tests when reintroduced.

### Critical 64-Bit Portability Fixes (Learned the Hard Way)
These bugs are subtle and WILL recur if new engine files are linked. Understand them before adding `ENGINE_SRCS`:

1. **GBA address-range checks break on host pointers.** Any engine code comparing a pointer against GBA constants (`IWRAM_END`, `EWRAM_START`, etc.) is wrong on 64-bit macOS — host pointers always compare "greater". Guard with `#ifdef PORTABLE` and check for `NULL` instead. Example: `IsTileMapOutsideWram` in `src/bg.c`.
2. **GameFreak string literals MUST go through `tools/preproc`.** The engine uses a custom charmap (`charmap.txt`), not ASCII. Strings are encoded bytes terminated by `EOS` (0xFF). If `_(x)` expands to `(x)` (plain ASCII), strings never terminate and `StringAppend`/text rendering walk off buffers and hang. All sources containing `_("...")` or `INCBIN_*` must be listed in `PREPROC_SRCS` in `Makefile.native` (piped through `clang -E | preproc | clang`), NOT plain `CFLAGS` compilation. Affected so far: `title_screen.c`, `sprite.c`, `text.c`, `text_window.c`, `text_window_graphics.c`, `strings.c`, `string_util.c`, `main_menu.c`, `new_menu_helpers.c`, `oak_speech.c`, `naming_screen.c`, `pokemon.c`, `battle_message.c`, `keyboard_text.c`, `util.c`, `battle_main.c`, `pokemon_icon.c`, `pokemon_storage_system_data.c`, `graphics.c`, `data.c`.
3. **DMA3 must be synchronous in PORTABLE mode.** `RequestDma3Copy`/`RequestDma3Fill` in `src/dma3_manager.c` perform instant `memcpy` and return immediately; `WaitDma3Request` always reports idle. The GBA queue-based path is guarded with `#else`.
4. **REG_VCOUNT must be 160 before `VBlankIntr()`.** `ProcessDma3Requests` and other engine code check `REG_VCOUNT > 224` to detect end-of-VBlank. `PPU_RenderFrame` leaves VCOUNT at 227; `src/main.c` `WaitForVBlank()` resets it to 160 each frame.
5. **`gFonts` must be initialized before any text is printed.** `SetDefaultFontsPointer()` now lives in the real `src/new_menu_helpers.c` (called via `InitTextBoxGfxAndPrinters`). If text prints with `gFonts == NULL`, `AddTextPrinter` silently no-ops or downstream code hangs.
6. **Save file status defaults to `SAVE_STATUS_EMPTY` (0)** in `src/platform/stubs.c` (`gSaveFileStatus`) so pressing START on the title screen starts a fresh game directly into character creation. It was previously hardcoded to 1 (`SAVE_STATUS_OK`) during early main menu porting to test the CONTINUE window, which caused interactive runs to select CONTINUE and hang on unlinked save-loading stubs.
7. **Software PPU video MODE 1.** Oak's Speech calls `InitBgsFromTemplates(1, ...)`: BG0/BG1 are text layers and BG2 is affine. `PPU_RenderScanline` has separate Mode 1 text and affine paths. Oak, the selected player portrait, and the rival naming icon are visually verified; the player-shrink transition remains to be checked after completing rival naming.
8. **Duplicate symbols when linking real engine files.** `src/platform/stubs.c` previously defined functions/data (`SetDefaultFontsPointer`, `DrawSpindaSpots`, `gMonFrontPicTable`, `gBattle_BG0_X`, etc.) now provided by linked engine files (`new_menu_helpers.c`, `pokemon.c`, `graphics.c`). When linking a real implementation, DELETE the stub version — never the reverse.
9. **Split sprite-sheet PNGs** (`name_0.png`, `name_1.png`, …) in `graphics/battle_anims/sprites/` must be combined into ONE png (vertically stacked, padded to width 64) before `gbagfx` 4bpp conversion; `gbagfx` cannot read them individually.
10. **`gbagfx` palette sources:** `INCBIN_U16("...gbapal")` sources are `.pal` (JASC) files, not PNGs. Convert `.pal → .gbapal → .gbapal.lz`.
11. **Naming-screen teardown spans the rest of the current frame.** `MainState_Exit` runs inside `RunTasks()`, changes the main callback, and frees `sNamingScreen`, but the old `CB2_NamingScreen` frame would otherwise continue into sprite animation and VBlank. Disable VBlank before freeing the state and return from `CB2_NamingScreen` immediately after `RunTasks()` when `sNamingScreen == NULL`.
12. **Stubbed sprite factories are unsafe for real scenes.** Returning 0 from `CreateObjectGraphicsSprite` is not a harmless no-op: callers mutate `gSprites[spriteId]`, corrupting whichever real sprite owns slot 0. Returning `MAX_SPRITES` is also unsafe when callers index without checking. Naming screens now create their icons from local, fully initialized templates; future callers must do the same or link the real object-event graphics path.
13. **`RegisterRamReset(RESET_REGS)` must restore affine identity matrices.** Clearing `REG_BASE` to zero collapses affine BG2/BG3 to one source pixel, hiding Oak and the player/rival portraits even though their tiles and maps are valid. After clearing registers, initialize `REG_BG2PA`, `REG_BG2PD`, `REG_BG3PA`, and `REG_BG3PD` to `0x100`.
14. **Real text tables must replace blank stubs completely.** The naming keyboard was blank because `battle_engine_stubs.c` supplied one-byte zero-filled `gText_NamingScreenKeyboard_*` arrays while `src/keyboard_text.c` was not linked. Add text-bearing sources to `PREPROC_SRCS` and delete every duplicate stub definition.
15. **Map headers, layouts, and script tables must use 64-bit host pointers.** GBA assembly `.4byte` pointers truncate 64-bit pointers on macOS ARM64. `tools/gen_map_data.py` compiles map layouts, headers, and event structures directly as native C structs in `src/maps.c`, where pointers are natively 64-bit (`sizeof(void *) == 8`).
16. **SaveBlock ASLR offset must be zero in PORTABLE mode.** GBA `SetSaveBlocksPointers` randomizes offsets up to 128 bytes assuming EWRAM padding. On macOS, save blocks are exact C struct buffers; adding an offset walks past buffer boundaries.
17. **Script command table (`gScriptCmdTable`) requires native function pointer sizing.** Script command dispatch indexes function pointers; on 64-bit architectures, this table must contain 8-byte pointers generated in C (`src/data/script_cmd_table.h`).
18. **`ForestMapPreviewScreenIsRunning` must return TRUE when idle.** In pret decompilation, this function returns whether the preview screen is *not* active. Returning FALSE keeps `FieldFadeTransitionBackgroundEffectIsFinished()` permanently false, preventing `Task_ExitNonDoor` from unfreezing objects and unlocking player controls upon warp entry.
19. **Map script headers must be terminated by 0x00.** Bytecode scripts terminate with `0x02` (`end`), but map header `.mapScripts` lists entries terminated by `0x00`. Using `0x02` causes `MapHeaderGetScriptTable` to overrun the array on frame-script checks.
20. **`src/menu.c` handles dialogue choice and cursor input.** Menu selection (`Menu_ProcessInput`, `Menu_InitCursor`, `Menu_MoveCursor`, `DrawStdFrameWithCustomTileAndPalette`, `CreateYesNoMenu`) was previously stubbed out in `battle_engine_stubs.c` returning 0, causing dialogue selection menus (such as Professor Oak's rival name choice box) to immediately choose option 0 (`NEW NAME`) and skip user interaction. `src/menu.c` is linked in `Makefile.native` with all duplicate stubs removed.
21. **Script command-table end must be a derived pointer, never a separate array.** The interpreter bounds-checks every opcode with `cmdFunc >= ctx->cmdTableEnd`. `gScriptCmdTableEnd` was a separate 1-element `ScrCmdFunc[]` array; the macOS linker placed it ~500 KB BEFORE `gScriptCmdTable`, so every command failed the bounds check, `ScriptContext_RunScript()` shut down instantly, and all field interactions (A-press on NPCs/signposts) silently did nothing — movement still worked because it bypasses the interpreter. It is now `const ScrCmdFunc *const gScriptCmdTableEnd = gScriptCmdTable + ARRAY_COUNT(gScriptCmdTable)` in `src/data/script_cmd_table.h`. `ScriptContext_SetupScript`/`RunScriptImmediately` must pass `gScriptCmdTableEnd` as a VALUE (no `&`).
22. **Header dependency tracking (`-MMD -MP`, `.d` files).** *Fixed — see the two traps below; keep them in mind if the flags are ever touched.* `Makefile.native` used to have no header dependency tracking, so changing a header included by a linked source did **not** recompile that object and `make` silently linked stale code. That is what made a `git pull` fail to link with ~40 undefined `_PalletTown_*`, `_ViridianCity_Mart_*` and `_gText_*` symbols: `src/data/maps_data.h` is a tracked generated header holding every one of them, the commit changed the header, and `src/maps.c` — its only includer — was untouched, so `maps.o` kept exporting the old symbol set while `main.o` (whose `.c` had changed) referenced the new one. Both rule families now pass `$(DEPFLAGS)` (`-MMD -MP`) and the bottom of the file does `-include $(OBJS:.o=.d)`.
    - **`-MT $@` is required, not optional.** clang names the dependency target after the output argument it saw. In the `PREPROC_RULE` pipeline the compiler that writes the deps is the `-E` stage, which has no `-o` — so the rule came out as `maps.o: …` instead of `build/native/maps.o: …` and attached to a target make never builds. The symptom is subtle: `.d` files appear, look correct, and make still plans nothing after a `touch`. Verify with `head -1 build/native/maps.d` — it must start with the full `build/native/…o:` path.
    - Dep tracking only records from the first build after it is added: an existing object with no `.d` still cannot see its headers, so the one rebuild that fixes a stale tree must be clean (`rm -rf build`). Later header edits rebuild correctly.
    - Because these are real dependencies, editing a widely-included header such as `include/global.h` now rebuilds all ~157 objects. That is correct; it used to plan nothing at all.
23. **The linker requires pointer relocations to be aligned.** Emitting `const void *` fields inside `__attribute__((packed))` structs (or byte-spilled `(u8)((uintptr_t)&sym >> n)` arrays) fails with `ld: pointer not aligned`. Native scripts therefore store pointer references as u32 INDICES into the aligned `gNativeScriptPtrs[]` table generated by `tools/gen_map_data.py`; `ScriptReadPtr()` in `src/script.c` resolves `gNativeScriptPtrs[ScriptReadWord(ctx)]`. Opcodes carrying pointers must call `ScriptReadPtr`, never `ScriptReadWord`.
24. **Pointer-typed operand ABI for native scripts.** `ScriptContext.data` is `uintptr_t[4]` on the host. Commands whose operands are addresses (`goto`/`call`/`goto_if*`/`call_if*`/`loadword` with labels, `applymovement`, `msgbox`, `special` table lookups) read host-width pointers via `ScriptReadPtr`; numeric/virtual operands (`vgoto`, `vmessage`, plain `.2byte`) stay `ScriptReadHalfword`/`ScriptReadWord`.
25. **macOS/SDL window-repaint quirk.** Occasionally a freshly launched window shows a stale mid-fade frame (a gray FireRed logo) even though the engine loop is healthy — confirmed via `sample`: PPU rendering, texture upload, and frame pacing all tick while the window shows the stale frame. Clicking/focusing the window redraws it. Not an engine bug; do not chase it in PPU/renderer code.
26. **Host pointers cannot be split across 16-bit task-data slots.** `SetWordTaskArg()` stores two 16-bit slots, so `SetWordTaskArg(taskId, N, (uintptr_t)ptr)` silently truncates on 64-bit. `Task_AnimateDoor` (`src/field_door.c`) packed `struct DoorGraphics *` and `struct DoorAnimFrame *` into two slots each and rebuilt a 32-bit pointer, so the FIRST door animation (stepping out of the front door) dereferenced garbage and crashed. Both operands are now stored whole with `memcpy` (`tFramesPtr`/`tGfxPtr`, four slots each on the host). The same trap existed in `src/new_menu_helpers.c` (`DecompressAndLoadBgGfxUsingHeap*` → `TaskFreeBufAfterCopyingTileDataToVram`), which freed a truncated buffer during the map transition; that path now uses the new `SetPointerTaskArg()`/`GetPointerTaskArg()` (`include/task.h`, `src/task.c`). Other `SetWordTaskArg(..., (uintptr_t)…)` sites remain in files that are not linked yet (`easy_chat_2.c`, `intro.c`, `pokemon_jump.c`, `pokemon_special_anim*.c`, `shop.c`) and in `src/fldeff_flash.c` (map preview, excluded under `PORTABLE`). Fix them the same way before linking those features.
27. **A coord event must never fall back to `sDummyScript`.** An inline `end` script is NOT inert for an automatic proximity trigger: `ProcessPlayerFieldInput()` → `TryStartStepBasedScript()` re-runs it every frame the player stands on the tile, `DoCB1_Overworld()` re-locks the field each time, and the player can never start another step — a permanent freeze. This is what stopped the player dead on Pallet Town's `(12,1)`/`(13,1)` Oak trigger. `tools/gen_map_data.py` now emits `.script = NULL` for any coord event whose script is not compiled natively; `TryRunCoordEventScript()` handles NULL (runs the weather trigger and returns) so the tile is simply walkable. Object and BG events keep `sDummyScript` — an A-press that does nothing is harmless there.
28. **Unported field effects must be no-ops, and the stub table must be full-size.** *(Superseded in part — field effects are now ported; see fix #49 for the script table and `FieldEffectScript_ReadWord`.)* `FieldEffectStart()` indexes `gFieldEffectScriptPointers[fldeff]` and then calls `sFldEffScrcmdTable[*script]`. The stub table was a single `{ NULL }` entry, so the tall-grass ground effect on the first step into Route 1 read out of bounds and jumped through a garbage command pointer. `FieldEffectStart()` returns 0 for a NULL script WITHOUT adding the id to the active list (otherwise waiters would hang forever) — that guard is still what keeps every not-yet-ported effect inert.
29. **Wild encounters must not start while the battle engine is stubbed out.** *(Superseded - the battle engine is now linked; `StandardWildEncounter()`'s `PORTABLE` early-out and the `StartWildBattle()` stub were both removed when encounters were re-enabled.)* `CheckStandardWildEncounter()` → `StandardWildEncounter()` → `StartWildBattle()` (a no-op stub) still returned TRUE, so `DoCB1_Overworld()` locked the field expecting a battle to unlock it later — walking into Route 1's tall grass froze the game with `locked=1, scriptRunning=0`. `StandardWildEncounter()` returns FALSE under `PORTABLE` (the battle engine is not linked); `StartWildBattle()`/`StartRoamerBattle()` remain stubs.
30. **Outdoor maps need generated `MapConnections`.** `MapHeader.connections` was hardcoded NULL, so `gMapConnectionFlags` stayed all-false, `GetMapBorderIdAt()` answered `CONNECTION_INVALID` in every direction (walling the player inside Pallet Town) and `InitBackupMapLayoutConnections()` had nothing to fill the neighbouring map into `VMap`. `tools/gen_map_data.py` now emits `struct MapConnection`/`struct MapConnections` from each `map.json` `connections` array (`up/down/left/right` → `CONNECTION_NORTH/SOUTH/WEST/EAST`, with `offset`, `MAP_GROUP()`/`MAP_NUM()`), which both draws the neighbour across the border and lets `CameraMove()` hand off via `LoadMapFromCameraTransition()`.
31. **Sprites whose top is above the screen must be clipped, not dropped.** `DrawSprites()` (`src/platform/ppu.c`) converted a wrapped OAM y (`y >= DISPLAY_HEIGHT` → `y -= 256`, i.e. 248 → −8) and then compared it against the scanline as `vcount >= (unsigned int)(y - half_height)`, so any sprite with a negative top failed the test and was skipped entirely instead of having its visible rows drawn. Overworld sprites use `coordOffsetEnabled` (map-space `sprite->y` plus `gSpriteCoordOffsetY` at OAM build time), so walking south in `PalletTown_PlayersHouse_1F` gives Mom at `(8,4)` an OAM y of 248 the moment the player reaches the room's south-most walkable row `(x,8)` — `CameraUpdate()` keeps the player ~4.5 tiles down the screen and pans 16 px per tile, and the room is only 10 tiles tall. She vanished for one row and returned one step north; the engine was not hiding her (`invisible=0`, `offScreen=0`, `oam.y=248`). The window check is now signed (`(int32_t)vcount >= y - half_height && (int32_t)vcount < y + half_height`); sprites fully above the screen (OAM y ≥ 256 − height) still stay hidden. Verified with a scripted `--skip-intro` walk (bedroom → 2F stairwell `(10,2)`, hold west → 1F → down to `(10,8)`): the pre-fix capture has no Mom, the post-fix capture draws her clipped at the top edge.
32. **The native `gSpecials` table must stay index-aligned with `data/specials.inc`.** `tools/gen_map_data.py` encodes a `special` as the opcode plus the special's *position* in the real specials table (`data/specials.inc`), and `ScrCmd_special`/`ScrCmd_specialvar` index `gSpecials` with it. The stub table in `src/platform/overworld_stubs.c` used to hold one entry (`HealPlayerParty`, index 0 by luck), so any other special was out of range and `AGB_ASSERT_EX` → `abort()` (fix the player sees: reading Oak's lab sign killed the game). Entries are now designated initializers keyed by the real index (`[0]`, `[368]`, `[369]`, `[371]`), unported slots stay `NULL`, and the `PORTABLE` dispatch prints `[Script] special N is not ported` instead of calling through `NULL` or aborting. 51. **A software PPU that ignores OAM affine matrices, display windows and HBlank DMA silently drops whole animations.** Three GBA subsystems the port originally stubbed out, each with a distinct symptom:
    - **Affine OAM sprites.** `gOamMatrices` was never read, so every rotated/scaled sprite drew upright and unscaled. The user-visible bug: the Poké Ball flew without spinning (the matrices were computed by `SpriteCB_BallThrow` but had no effect). The compositor now inverse-transforms each pixel through `gOamMatrices[oam.matrixNum & 0x1F]`. Double-size affine sprites (`(oam->affineMode >> 1) & 1`) cover a doubled bounding box but index their tile block using the object's **undoubled** dimensions, so `block_offset`'s stride uses `src_width`, not the doubled `width` — using the doubled width samples the wrong tiles. Flip is meaningless for affine sprites (the matrix carries the sign) and must not be applied on top.
    - **Display windows (`REG_WIN0H`/`REG_WIN0V`/`REG_WININ`/`REG_WINOUT`).** Zero references before; every window-masked screen composited as if unmasked. The battle transitions wipe by animating WIN0, and the OPTION menu dims everything except the cursor row, so both rendered as a plain fade. `ComputeWindowMask()` resolves region priority WIN0 > WIN1 > OBJWIN > outside per pixel. Two traps: masking must be **inactive** unless a window is actually switched on in `REG_DISPCNT` (else a stale `REG_WINOUT` mutes the whole screen), and an OBJ-window sprite is **not drawn** — its opaque pixels only mark the region (regardless of its blend/priority bits), so the old code's "draw it if WINOUT allows" branch was wrong.
    - **HBlank-timed DMA.** `DmaSet` compiled to `do {} while (0)` under `PORTABLE`, so per-scanline effects never wrote their register. `PortableDmaSet` now records the channel and `Platform_RunHBlankDma()` replays one transfer per rendered scanline from inside `PPU_RenderScanline`. Only `DMA_START_HBLANK` channels are recorded; `DMA_START_NOW` still runs inline via `PortableDmaCopy`. The replay must run **after** the scanline is composed and takes effect on the *next* one — the engine's VBlank callback arms the channel from `buffer + 1` precisely because the first entry is consumed by the hand-written register store, which is why `RenderFrame` seeds the buffer one entry in. The channel's source advances and its destination stays put (DMA0's destination is fixed/reload, not incrementing — see fix #52).

    All three are pure compositor gaps, not engine gaps: the engine computed the matrices and wrote the registers correctly the whole time. When a whole class of animation is missing but the engine logic runs, check whether the PPU reads the register the engine writes.

52. **The DMA control word packs flags in the high halfword and the transfer count in the low one.** `Platform_RunHBlankDma()` read its source-step and destination-step bits straight out of `ch->control` (`(control >> 7) & 3`, `(control >> 5) & 3`), which reads the **count** — 1 for every HBlank arm site — not the flags. That decoded `B_TRANS_DMA_FLAGS` (`count 1`, `DMA_SRC_INC`, `DMA_DEST_FIXED`) as "source increments, destination increments", so each scanline's transfer wrote one register further along: scanline 0 hit `REG_WIN0H`, then `WIN0V`, `WIN1H`, `WIN1V`, `BLDCNT`, `BLDALPHA`, `BLDY`, `MOSAIC`, and on into the rest of `REG_BASE`. Register dumps showed every one of those registers holding the walking source values (`47F1`, `00A9`, `61F1`, …). The window then had no horizontal bounds and the blend registers were garbage, so the field was masked to near-black with only a few slices of background surviving — the "artifacting" seen when entering a wild battle (Slice and White-Bars-Fade both use WIN0H via DMA). It also silently corrupted the window/blend state for the whole transition, and `BLDALPHA`'s clobber would have degraded any simultaneous blend.

    The flags must come from the high halfword: `ctrl = ch->control >> 16`, then `(ctrl >> 7) & 3` / `(ctrl >> 5) & 3`. Every HBlank arm site in the engine is DMA0 with `DMA_DEST_FIXED` (`B_TRANS_DMA_FLAGS`) or `DMA_DEST_RELOAD` (`SCANLINE_EFFECT_DMACNT_16BIT`/`_32BIT`), and the count is always 1: the source walks the per-scanline buffer while the write stays pinned to one register, so `count` only ever means "one register write per scanline". The destination step is honoured as fixed/reload (2 and 3) and increment (0); DMA0 is the only channel the engine arms this way.

    `TestOverworldInteractions()` now arms a fake HBlank channel at a 4-entry destination array and asserts the transfer lands on entry 0 every scanline with entries 1–3 untouched, so a reintroduced low-halfword read fails loudly at startup rather than at the next battle transition.

53. **A green build on one machine is not a buildable tree.** `make -f Makefile.native` worked here only because this working copy carried artifacts a fresh clone never has — and every one of them was gitignored, so nothing produced them. A `git clone` + `make` failed at the first asset rule and kept failing deeper in. Four separate gaps, each capable of hiding the others:

It must not invoke make — it runs from inside the Makefile. And `graphics_file_rules.mk` is pret's file kept verbatim except for one deletion: its `redyellowgreen_frame.bin` rule `cat`s four frame `.bin` files that exist neither here nor upstream while the concatenated result **is** tracked.     Verify build-system changes from a real clone (`git clone . /tmp/x && cd /tmp/x && make -f Makefile.native`), never from the working tree: the untracked artifacts here make local success meaningless.

54. **A big prerequisite list on a target the top-level make walks makes GNU Make 3.81 spin under `-j`.** The symptom is unmistakable once seen: `make -f Makefile.native -j8` never finishes, `sample` shows make recursing inside its own dependency code (`+0x15e0c` ↔ `+0x17714`), **no child process is ever started**, and CPU sits at 100% (or, on some runs, wall time is far larger than user time because make is stat-ing). The same tree builds in ~29 s with `-j1`. It is not a cycle — make prints no circular-dependency warning, and `overriding commands` is 0.

    The trigger is list *size*, and bisection pinned it exactly: a target carrying 1178 prerequisites is fine; 1179 spins. The 1179th entry was an ordinary `graphics/battle_anims/backgrounds/attract.4bpp.lz`, so it is a threshold, not a special file. Concretely, `assets: … $(INCBIN_ASSETS) …` with the derived list (~6400 paths) was enough on its own; removing just that token from the line turned a >60 s wedge into 0.6 s with no other change.

    Structure that avoids it (and the reason `Makefile.native` looks the way it does):
    - The large list is never a prerequisite in the graph object compilation walks. `$(OBJS)` takes one real-file stamp (`build/native/.assets.stamp`) order-only; the stamp's recipe drives the two asset phases through sub-makes.
    - Those sub-makes **must** pass `-j1`. A sub-make inherits `MAKEFLAGS`, so a parallel one reproduces the identical spin internally — the first attempt at this fix hung for exactly that reason.
    - `all` does not name the phony `assets` target: a phony target with thousands of prerequisites gets re-walked from every dependent.

    Related trap found in the same file: `.PHONY` on a *generated* target makes it unconditionally out of date. 63. **A `FORCE`d target with a separate object branch races under `-j` — and the recipe's `mv` then hid the failure.** `make tests -j8` from a clean tree died with `clang: error: no such file or directory: 'build/native/tests/mom.o'`, **exited 0**, and left no `firered-tests` binary. Two independent defects in one rule; either alone is worth knowing. The structure was:

    ```make
    tests: $(TEST_OBJS) $(TARGET_TESTS)          # two INDEPENDENT branches
    $(TARGET_TESTS): $(TEST_ENGINE_OBJS) FORCE   # recipe runs immediately
    ```

    The two prerequisites are siblings, so `-j` schedules both at once. Because `$(TARGET_TESTS)` carries `FORCE`, its recipe is never considered up to date and runs *immediately*, linking against `$(TEST_OBJS)` while those objects are still compiling. The `$(TEST_OBJS)` branch only gated the phony `tests` target, which never waits for the sibling.

    The intent behind that shape is real and worth preserving (see the comment block above `tests:`): make decides staleness *before* running any recipe, so it cannot observe a **deleted test source** — that is not a change to a tracked prerequisite — and a stamp or a self-remaking include both raced make's one-second timestamp resolution intermittently, which is worse than failing loudly. So the link recipe deliberately computes its own inputs (pruning objects whose source is gone, relinking when the object set changed).

    The fix is to keep that design and restore only the ordering, with an **order-only** prerequisite:

    ```make
    $(TARGET_TESTS): $(TEST_ENGINE_OBJS) FORCE | $(TEST_OBJS)
    ```

    Order-only is exactly right here: it guarantees the objects exist before the recipe runs (which is all that was missing) without adding timestamp-based staleness on top of the check `FORCE` already forces. A plain prerequisite would also have worked but would let make *also* decide relinking from object mtimes — the thing that intermittently mis-fired before.

    **The race was silent for a second, independent reason, and that half is the more dangerous one.** The link recipe's compile sits inside an `if` shell block followed by `mv`, so the compile's failure status was swallowed by the `mv` that succeeded after it:

    ```make
    $(CC) ... -o $@;                        # fails; shell continues (no set -e)
    mv $(TEST_OBJ_LIST).tmp $(TEST_OBJ_LIST);   # succeeds → if-branch status 0
    ```

    `make tests -j8` therefore **exited 0 with no `firered-tests` binary on disk** — verified directly (`REAL EXIT CODE = 0`, `ls: firered-tests: No such file or directory`). A CI job would have reported success while testing nothing. The compile now ends in `|| exit 1`; a deliberately-broken test source makes the build exit **2**, and because the failing link never reaches the `mv`, `.linked-objects` is not poisoned and the next build recovers on its own.

    Verified: `rm -rf build/native/tests && make tests -j8` 12/12 clean (and 12/12 again after hardening the exit status); adding a test source appears under `-j8`; deleting one still prints `[tests] removing stale …` and drops it from the binary; a no-op rebuild does not relink; a deliberately-broken source exits nonzero; and a fresh `git clone` builds both `all` and `tests` under `-j8` with 58/58 passing.

    The generalisable rules: **a `FORCE`d recipe that consumes the outputs of a sibling prerequisite is racy under `-j`** — anywhere a recipe reads files another branch of the same target produces, that branch must be reachable from the recipe's own target (order-only if you want the files but not the timestamp semantics). And **a multi-command recipe line only reports its last command's status**, so a compile followed by a `mv`/`touch`/`cp` fails silently; end the essential command with `|| exit 1`, and check `$?` when you introduce one rather than trusting a pipeline's status.

    Pinned by `tests/battle_anim.c` (three tests): the affine task walks its table (and follows a re-pointed one, which a stale side table would break), and the shake writes the *named register* and restores it. All three SEGV without their fix (`AnimShakeMonOrBattleTerrain + 104`).

    Two audit findings in this family were **discarded as unreachable**, which is the part worth repeating: `src/battle_anim_effects_1.c:5059` stores a palette mask (an `int`, not a pointer) and `src/battle_anim_fight.c:797` stores `sprite->y << 8` — both round-trip a *number* through `StorePointerInVars`, which is correct as written. And `include/fldeff.h`'s `FLDEFF_SET_FUNC_TO_DATA`/`FLDEFF_CALL_FUNC_IN_DATA` do truncate a function pointer, but every user (`fldeff_cut.c`, `_dig.c`, `_rocksmash.c`, `_strength.c`, `_sweetscent.c`, `_teleport.c`) is unlinked, so the macros are currently inert — they are a landmine for whoever links the field-move effects, not a live bug. **Check linkage (`nm`/`Makefile.native`) before acting on an audit finding; three of this pass's candidates were in files no binary contains.**

67. **A struct field read through the wrong base pointer is a silent scaling error, not a crash.** The mixer's envelope stage ends with `ldr r0, [sp, 0x18]; ldrb r0, [r0, o_SoundChannel_release]; adds r0, 0x1; muls r0, r5; lsrs r5, r0, 4`, then scales both channel output volumes by `r5`. The slot `[sp,0x18]` holds the **SoundInfo** pointer (the same slot is read four lines earlier for `o_SoundInfo_divFreq` and `o_SoundInfo_maxChans`), so `o_SoundChannel_release` — the value 7 — lands on `SoundInfo.masterVolume`, which is at offset 7 (`ident` 0..3, `pcmDmaCounter` 4, `reverb` 5, `maxChans` 6). Reading the channel's own `release` byte instead scales every channel by ~1/16: the game still runs, the song still sequences, and the mix is merely very quiet — the hardest kind of audio bug to notice, because nothing is obviously broken. When transcribing assembler that reads a struct through a saved pointer, check which struct that pointer actually is before trusting the field name.

    Pinned by `tests/sound.c`, which asserts `envelopeVolume{Left,Right}` equals the master-volume formula rather than merely being non-zero.

68. **A four-byte word store is several field assignments, and the assembler will not tell you which.** `ply_note` gives a channel its note fields with one instruction: `ldr r0, [track, o_MusicPlayerTrack_gateTime]` / `str r0, [chan, o_SoundChannel_gateTime]`. Because `MusicPlayerTrack` is `{flags, wait, patternLevel, repN, gateTime, key, velocity, runningStatus}` and `SoundChannel` is `{..., gateTime, midiKey, velocity, priority, rhythmPan, ...}`, that single store copies **four** bytes — `gateTime→gateTime`, `key→midiKey`, `velocity→velocity`, `runningStatus→priority` — and the compiler gives no hint that `velocity` was written, because nothing in the source names it. `ChnVolSetAsm` scales the channel volume by `velocity`, so transcribing only `chan->gateTime` leaves it 0 and every PCM channel mixes silence while the sequencer runs perfectly. Search the assembler for `str` of a multi-byte field into a struct whose neighbours are also fields, and write out each byte that lands.

    Pinned by `tests/sound.c` (a live channel's `velocity` and per-side volumes must be non-zero).

69. **A label in a byte stream is a position, not a separate object.** mid2agb emits each song track as a series of labels (`mus_x_1`, `mus_x_1_B1`, `mus_x_1_B2`) and the interpreter **runs off the end of one into the next** — that is what the assembler's contiguous layout means, and mid2agb relies on it (a track's first label is often two bytes, `KEYSH 0`, with the real song in the block after). Emitting each label as its own C array breaks that: `mus_pallet_1` became a 2-byte array whose continuation depended on linker placement, and the track read whatever rodata happened to follow instead of its first block. Each track is now emitted as one array with its labels as offsets (`#define mus_x_1_B1 (&mus_x_1_Data[2])`), which reproduces the layout exactly. The failure is layout-dependent and therefore intermittent-looking — it reproduced in the test binary but not the game binary — so treat "works in the game, fails in tests" as a signal to look for this class rather than at the test.

    Pinned by `tests/sound.c`: a song plays, sequences, and mixes non-silent audio.

70. **An active-low hardware register that powers up zeroed means "everything pressed".** `REG_KEYINPUT` is active low, and `REG_BASE` is zero-initialised, so on the first `ReadKeys()` — which runs before `Platform_UpdateInput()` has written the real SDL state from the frame loop — `keyInput = REG_KEYINPUT ^ KEYS_MASK` is `0x03FF`, i.e. every button held. The engine's soft-reset check tests A + B + START + SELECT on `heldKeysRaw` and fired immediately, calling `DoSoftReset()`. The damage was invisible for as long as every function `DoSoftReset` calls was a stub; once the sound driver became real, its `m4aSoundVSyncOff()` parked `SoundInfo.ident` at `ID_NUMBER + 10` and the sound system stayed disabled for the whole session. `REG_BASE` is now seeded with a designated initializer (`[0x130] = 0xFF, [0x131] = 0x03`) and `RegisterRamReset(RESET_REGS)` restores the same value after its `memset`. **A stubbed-out subsystem hides the side effects of the code paths that call into it** — expect a wave of these as each one is linked.

71. **A stub is not the only way to be silent: a declared, defined, test-stubbed function with no caller looks exactly like working wiring.** `Platform_SubmitAudioFrame()` existed in `include/platform/platform.h`, was fully implemented in `src/platform/sdl2.c` (queueing frames, resampling 13.379 kHz to the device rate), and was stubbed in the harness — and **nothing called it**. The whole sound port therefore appeared complete: `m4aSoundInit` ran, `m4aSoundMain` mixed into `gSoundInfo.pcmBuffer` every vblank, the SDL device opened and printed `[Audio] opened 48000 Hz stereo audio device`, and the game was silent. The call belongs in `VBlankIntr` immediately after `m4aSoundMain()` (the buffer must be *this* vblank's mix, not the previous one's), which is what the surrounding comments and AGENTS.md both already claimed — the claim was true of the design and false of the code.

    Two things hid it, and both generalise:

    - **The existing tests asserted the wrong side of the seam.** Three tests read `gSoundInfo.pcmBuffer` directly and passed, because the *driver* was correct. They would pass with the handoff deleted, which was verified by deleting it: `sound/playing a song mixes non-silent audio`, `sound/a channel is given the track's velocity and key` and the pointer/voice-data tests all stayed green while the game was silent. A test that observes the producer cannot catch a broken consumer. The regression test (`sound/the engine hands its mix to the platform every vblank`) asserts through the harness's recording of the real call site — `gHarnessAudioSubmits`/`gHarnessAudioMagnitude` in `tests/platform_host.c` — so it fails (`both 0`) on the pre-fix tree and reports one submit per frame afterwards.
    - **`SDL_Init` did not request `SDL_INIT_AUDIO`** (`SDL_INIT_VIDEO | SDL_INIT_TIMER | SDL_INIT_GAMECONTROLLER`). `Platform_InitAudio()` calls `SDL_InitSubSystem(SDL_INIT_AUDIO)` itself, so the device opened anyway, which is why this was not the cause — but leaving the subsystem out of the top-level init is a latent trap, and it is now named there.

    The generalisable rule: **when a subsystem is inert, check for a missing call site before reading the implementation.** Grep the function's name across the tree; a symbol that appears only in its declaration, its definition, and a test stub has no caller. `grep -rn "Platform_SubmitAudioFrame"` would have found this in seconds at any point during the original work.

72. **`SoundMix`'s clear must cover both PCM halves, and it is reached on the reverb-off path.** `MixChannel` *accumulates* into `pcmBuffer` (`mixR[i] = mixR[i] + ...`), so any half that is not cleared first keeps the previous vblank's samples and each note piles on top of them — the channel saturates rather than plays. The assembler's clear loop walks `r5` (`pcmBuffer + cursor`) and `r6` (`r5 + PCM_DMA_BUF_SIZE`) in lockstep with paired `stm r5!`/`stm r6!` stores, clearing `pcmSamplesPerVBlank` bytes in **each**; the port's `memset(soundInfo->pcmBuffer, 0, samplesPerVblank)` cleared only the right half. The reverb block above it already writes both halves, so the defect lives specifically in the reverb-off branch — which is where a song whose header clears reverb lands, and where the driver sits before the first reverb-setting song starts. Verified with a temporary probe in the real SDL binary that the live field-music path reports `reverb=50` (the reverb branch) and both channels carry signal (`peakR=30 peakL=40`) with the queue draining, so the probe measured the branch correctly rather than assuming it.

    Pinned by `sound/each vblank clears both PCM halves before mixing`, which forces `reverb = 0` and `maxChans = 0`, poisons both halves with `0x55`, and requires every byte back cleared — it fails on the single-`memset` version with `byte 0 of the LEFT PCM half survived the clear`. Note the two probes used to establish the reverb value and the per-channel peaks were temporary and have been removed; the value is recorded here rather than re-measured.

73. **A hardware subsystem the engine drives but the port never reads is silent, and "the engine is correct" hides it.** The GBA has two sound sources and M4A feeds both. `SoundMainRAM` mixes PCM into `SoundInfo.pcmBuffer` and `src/platform/sdl2.c` drains it — that half worked. `CgbSound()` (`src/m4a.c`) computes each CGB channel's envelope, period and duty each vblank and writes the `NR10`..`NR52` registers — and **on hardware those registers are the oscillators**. Under `PORTABLE` they were ordinary bytes in `REG_BASE` that nothing ever read, so pulse 1, pulse 2, the wave channel and the noise channel were all silent.

    Nothing pointed at it. No stub, no error, no crash, no warning, and the engine code was a faithful, complete implementation of the PSG envelopes. The game made sound, so "audio works" was a reasonable conclusion — and it was wrong for whole instrument layers: the title theme drives 2 CGB voices of 6 tracks, Pallet Town 2 of 6, `mus_lavender` 2 of 9, and `mus_pewter`/`mus_sevii_123`/`mus_poke_tower`/`mus_vs_deoxys` 1 each. Quantified on the real binary by disabling the call site and diffing what the SDL callback played, the missing channels were **32.9% of the mix energy** on the title theme (RMS 1126 -> 1193, peak 5888 of 32768, 9.4% of samples changed).

    The fix is `src/platform/psg.c`: synthesise the four channels from the registers the engine already wrote, exactly as the software PPU renders from the video registers. Both PSG and DirectSound are summed into the same two PCM halves, because `SOUNDCNT_H`'s `SOUND_CGB_MIX_FULL` routes them into one DAC. Three details cost real time and generalise:

    - **Read a channel's *level* from the engine, not from its register.** NRx2's high nibble is the envelope's *initial* volume and its low nibble instructs the hardware envelope unit; M4A writes 0 there when a note attacks from silence and keeps the running value in `CgbChannel.envelopeVolume`. On a live note NRx2 held `0x09` (initial volume 0) while the engine's envelope climbed 0,1,2,3,4 — so a register-derived level is a permanent zero. The same is true of panning in the other direction: NR51 *is* live (CgbSound rewrites it through `panMask` every vblank) while `CgbChannel.pan` is the engine's copy, so panning comes from the register. Check which side is authoritative per field instead of assuming the struct is always right or the register always is.
    - **Scale the 4-bit DAC to the PCM byte, or low volumes vanish.** A CGB level is 0-15; centring it and dividing by the duty cycle puts envelope 1 at +/-0.5 and rounds every sample to zero. The game's music uses envelope 1-4, so the synthesiser computed the correct waveform and emitted nothing — the failure looked identical to "the registers are never read". `PSG_DAC_SCALE` (8) puts full envelope at +/-60 of the 8-bit range and envelope 1 at +/-4.
    - **Saturate; do not let the byte wrap.** The DirectSound mix already occupies most of the 8-bit range and PSG is summed on top. A plain `(s8)` cast turns an overflow into a sign flip, which is gross harmonic distortion; the hardware sums in the analogue domain and clips. Saturating reproduces that.

    The level of the CGB voices is genuinely quiet in this game (envelope 1-4 of 15), so the *character* of the fix is restored layers rather than a loudness boost — worth knowing before "I can't hear much difference" is read as "the fix did not work". A test that only asserts non-silence passes either way; the tests assert the waveform alternates, the pitch matches the programmed register period, the gates are respected, and `SoundMain` itself reaches the synthesiser.

74. **A resampler is not plumbing: a hold is an audible artefact and 8-bit units destroy an interpolation.** The seam between the engine's 13,379 Hz PCM and the host device's rate is where "choppy" came from, and it held three separate defects, each measurable and each invisible to the others' tests.

    - **A zero-order hold is not a neutral choice.** Repeating each engine sample 3.6 times leaves a step train whose spectrum is the source band mirrored around the engine rate and folded back into the audible range. On a real run's buffer the hold put **2.27% of the output's energy above the source Nyquist, with its largest image at 11.9 kHz from a ~1.5 kHz tone** -- a whistle that was never in the signal and that no emulator produces. Linear interpolation takes it to 0.12% modelled, 0.36% measured. The comment that had defended the hold ("interpolating would invent detail the hardware never had") was exactly backwards: the hardware reconstructs a continuous DAC output with far better anti-imaging than either option, so the hold was the one adding artefacts.
    - **Interpolate in the output's scale, not the sample's.** One 8-bit step is large next to one output frame -- engine samples are 48000/13379 = 3.59 frames apart, so the blend fraction never exceeds 0.84, and a delta of 1 or 2 sample units truncates to zero for every frame in the interval. Performed in sample units, an "interpolation" degenerates to the hold for precisely the small deltas that make up a quiet passage (it measured 0.43% instead of 0.12%). Shift the delta up first, and widen the product: `255 << 8` times 48000 overflows `s32`.
    - **Carry the sub-sample position across the seam.** Each vblank is 803.6475 output frames; restarting the position inside each one discards that 0.6475, which is **176 frames of drift per 500 vblanks (~0.04%)** and accumulates into a slow pitch rise against the DirectSound layers still in tune. A waveform check cannot see this -- the error is in timing, not amplitude, so the signal stays smooth while playing at the wrong rate; assert the **output frame count** over many vblanks instead.

    Locate this class with two measurements rather than by ear: the **spectrum above the source Nyquist** (imaging), and the **jump statistics at vblank boundaries against a random-interior control** (the seam). The control matters: a boundary mean taken alone looks alarming even when it is chance. Before the fix 29% of boundaries exceeded the interior p95; after, 9.3%, which is the ~10% a 95th percentile predicts.

    Two things worth not wasting time on, both checked here: the SDL queue underruns only while it primes (counting underruns **after** the 50th callback showed zero over 400 frames), and the PSG total peaks at only +/-21 so its clamp was not the symptom. When a symptom is reported by ear, measure the candidate causes before changing them.

75. **A wide store over adjacent struct fields is several field assignments, and the compiler will not tell you which — this one made every note die after five vblanks.** `ply_note` installs a note by copying the voice's envelope onto the channel. The assembler does it in two instructions (`src/m4a_1.s` lines 1755-1758):

    ```
    ldr r0, [r6, o_ToneData_attack]                    @ ToneData{ attack, decay, sustain, release }
    str r0, [r4, o_SoundChannel_attack]                @ SoundChannel{ attack, decay, sustain, release }
    ldrh r0, [r5, o_MusicPlayerTrack_pseudoEchoVolume]
    strh r0, [r4, o_SoundChannel_pseudoEchoVolume]     @ + pseudoEchoLength
    ```

    `struct ToneData` is `{ type, key, length, pan_sweep, wav, attack, decay, sustain, release }` and `struct SoundChannel` has the same four envelope bytes in the same order, so one 32-bit store copies **all four**; the 16-bit store copies the echo volume *and* length. The port wrote only `chan->attack = tone->attack` (and only `pseudoEchoVolume`), so `decay`, `sustain`, `release` and `pseudoEchoLength` stayed 0 on **every channel of every note, for the whole game**.

    The envelope state machine turns that into a hard kill, not just a wrong timbre. Attack runs to 255, `statusFlags--` moves it to the decay stage, and decay computes `volume = (volume * 0) >> 8 = 0`; that is `<= sustain` (0), and `pseudoEchoVolume == 0` takes the "turn off" branch. So a note sounded for exactly as long as its attack ramp lasted — **5 vblanks at attack 51 of 255** — and then the channel was switched off, whatever the voice's real envelope said. Measured over the field music, **25.8% of the output frames were exact digital silence, in 1,581 separate dropouts**, with the channel state flipping ON → OFF every few vblanks. That is the "stuttering, cutting in and out"; the ~375 Hz repetition rate of those drops is the buzz. The zeroed `pseudoEchoLength` also removed the release tail, so notes stopped dead instead of fading.

    After the fix the same measurement gives **2.1% silence, RMS 828 → 2167, peak 9958 → 25533** with nothing at the rail. `tests/sound.c`'s `sound/a channel carries the voice's decay, sustain and release` asserts the relationship rather than a literal — an ON PCM channel must have at least one of decay/sustain/release non-zero, because the generator emits them straight from `voice_groups.inc` and a real voice never has all three zero — so it fails on the historic defect (`expected true: distinct > 0`) and is independent of which voice the song picks.

    This is the third instance of the same family (#67 `SoundInfo`-vs-channel base pointer, #68 the same in `ply_note`, #75 here): **when transcribing a `ldr`/`str` of a multi-byte field into a struct whose neighbours are also fields, write out every byte that lands.** `grep` the assembler for `str` whose source and destination are both multi-byte struct fields and check each one against the C.

76. **A square wave sampled at the engine's rate aliases, and no amount of resampler care can undo it — the harmonics are already folded into the 13.4 kHz signal.** The PSG pulse channels were synthesised as a naive square: `value = (pattern >> step) & 1 ? highLevel : lowLevel`, sampled once per engine sample. A pulse *is* the sum of its odd harmonics, so sampling it does not remove the ones above the source Nyquist — it mirrors them back **below** it, inharmonically. Measured on a duty-50% note at register 1978 (1872 Hz), the 5th and 7th harmonics (9360 and 13104 Hz) folded to 4017 and 272 Hz. That is the buzz heard over Route 1, and because the folded tones are inside the source band, the resampler's stop-band and the device's own reconstruction both pass them untouched. It also moves the perceived pitch of short notes, since the folded partials are the loudest thing in the attack.

    The fix is a band-limited table: `sPulseTable[4][64]`, each row `8 * (2/(n*pi)) * sin(n*pi*d) * cos(n*t)` summed over odd `n` up to 13. 13 x 2048/60.2 = 442 Hz is the highest fundamental the period register can reach, so its 13th harmonic is 5.75 kHz — under the 6,689 Hz Nyquist at *every* pitch the hardware can be asked for, which is what makes a fixed harmonic count safe rather than a compromise. `value = (table[idx] * volume * PSG_DAC_SCALE) >> 3`. Measured on the same capture, the 2–4 kHz band (where this song's folded products land) drops from 15.05% to 10.38% of the spectrum at equal loudness.

    `tests/sound.c`'s `a CGB pulse carries no harmonics folded below the source Nyquist` names the bins: it mixes a duty-50% pulse at register 1978 and requires the energy at 4019 Hz and 275 Hz — where that pitch's 5th and 7th harmonics land — to be under 1% of the energy at the harmonics that belong there. It fails on the naive square and passes with the table. The wave channel has the same problem in principle; its `WAVE_RAM` patterns are low-harmonic by construction in this game, so it was left alone rather than pre-optimised.

77. **A synthesiser's output scale is a balance decision, and getting it wrong is audible as a different instrument being too quiet.** `PSG_DAC_SCALE` was chosen to make one CGB channel audible (`+/-60` at full envelope, "the same order as one DirectSound channel"); the choice that matters is the ratio the *DAC* sees. Measured on Route 1 by averaging `|PSG|` and `|DirectSound|` per sample inside the mixer, scale 8 left the CGB channels at **73.5% of the output amplitude** — 66% of its energy — so the accompaniment and counter-melody sat on top of the melodic line. The user-visible symptom was not "the PSG is too loud" but **"the melody is too low of a volume while the harmony is fine"**, which is the same fact described from the other end. At scale 4 it is 58.9%.

    Two things generalise. Measure the balance *inside the mixer*, per sample, by mean absolute value: doing it by subtracting two captured runs is unreliable because the capture is not sample-aligned across boots, and the difference then exceeds either signal (it measured 127% of the mix's energy, which is not physically possible and is the tell). And when a layer is "too loud", check whether the user described another layer as "too quiet" — the fix is one number, and the wrong description sends you looking at the wrong channel.

    **What is measured and what is not.** The ratio itself is solid: `|PSG|` and `|DirectSound|` are averaged over the *same* sample inside `Platform_PsgMix`, so no alignment or drift can corrupt it, and it is a fact about the port. What is *not* measured is the target. The natural guess — that the hardware attenuates the CGB channels, so `SOUNDCNT_H`'s ratio bits would explain the right scale — is wrong: `m4aSoundInit` programs `SOUND_ALL_MIX_FULL` (0x000E), i.e. CGB at 100% and both FIFOs at 100%, and `CgbSound` sets NR50 to 0x77 (both master volumes at max). So the engine sums all three sources at full weight and the real balance is set by the *voice volumes in the song data*, not by a hardware ratio. Nothing at 25% or 50% explains the number. **`PSG_DAC_SCALE = 4` is therefore an empirical starting point, not a derivation, and the final value needs the project owner's ear** — that is a decision to hand to them rather than to pick from an unsupported model of the hardware.

    `tests/sound.c`'s `the CGB layer sits under DirectSound, not over it` asserts the relationship: a full-envelope pulse mixed against a DirectSound layer of the field music's measured magnitude (mean |sample| 4 of 127) must not dominate it. It fails at scale 8 and passes at 4.

### Native Frame Timing
- **The game clock is not the display clock.** The original native loop relied on `SDL_RENDERER_PRESENTVSYNC` without an independent timer; that allowed high-refresh presentation to accelerate frame-based gameplay, while the fallback renderer did not explicitly request VSync. This timing gap was found after movement appeared too fast. The pre-fix runtime frame rate was not measured.
- **Target the hardware frame period:** 280,896 CPU cycles per frame at 16,777,216 Hz, or approximately 59.7275 Hz (16.7427 ms per tick). Do not change movement speeds, animation counters, or emulate CPU clock speed to compensate for host performance.
- **One pacing owner:** `WaitForFrameDeadline()` uses `SDL_GetPerformanceCounter()` / `SDL_GetPerformanceFrequency()` and absolute deadlines. Time spent in the engine and renderer counts toward the next deadline; `SDL_Delay()` sleeps rather than busy-spins. Do not add a fixed sleep after every frame or a second limiter in `WaitForVBlank()`, the BIOS shim, or the standalone test.
- **VSync is deliberately disabled** in renderer creation so monitor refresh does not set engine speed. Do not re-enable it as a replacement for the game clock; any future presentation changes must preserve independent simulation timing.
- **Stalls do not accumulate catch-up ticks.** When the next deadline is already past, the clock resynchronizes to one frame after the current time. Sustained overload slows the game rather than skipping engine updates.
- **Verification:** Metal and software renderers were exercised with 4 ms of simulated engine work per frame. For 300 frames, elapsed times were 5.022 s and 5.049 s respectively (target 5.023 s). Both recovered from a 500 ms stall without a catch-up burst. A real 9,300-frame engine boot completed in 155.92 s (frame-time target 155.71 s plus startup), with bedroom spawn confirmed in the capture. The standalone 120-frame PPU test also passed. Temporary timing probes were removed.

### Debugging Tips
- **Boot tests now run at game speed:** allow roughly `N / 59.7275` seconds plus startup for `--boot-test N`; 9,300 frames take about 156 seconds. Use a timeout above that duration. The assertions that used to run inside the game binary (`--test`, `TestBiosSyscalls`, `TestGbaMemory`, `TestOverworldInteractions`, `Platform_VerifySaveBackedStubs`) now live in `tests/` and run under `./firered-tests`; the `--test` mode is gone.
- Boot test with N frames: `./firered-native --boot-test N` (saves `engine_boot_output.bmp` at frame N). The boot test auto-presses: START at frames 5–10 (skip intro fade), 30–35 (enter game from Title Screen), DOWN at 230–231 + A at 240–245 (select NEW GAME), then A at 320–325 / 360–365 / 400–405 / 520–525 / 560–565 (advance Controls Guide → Pikachu intro → Oak speech). Starting at frame 620 it also presses A for 6 frames every 90 frames. This periodic input advances Oak's dialogue, gender selection, player naming, rival naming (frames 6500–7200), farewell speech (frame 8600), hands off to `CB2_NewGame` by frame ~8900–9000, and spawns into the player's bedroom in Pallet Town (`CB2_Overworld`) by frame 9200.
- Fast overworld iteration: `./firered-native --skip-intro --boot-test 200` reaches the bedroom (fresh save, `RED`/`GREEN`) in ~3.5 s instead of ~156 s for the 9,300-frame full boot. Byte-identical captures across runs (RNG is seeded from a host-zeroed timer).
- Warp anywhere without walking: `./firered-native --skip-intro --dev-panel --dev-panel-keys "WAIT*60,TAB,O,A,K,S,WAIT*10,ENTER,WAIT*170"` lands in Oak's Lab (~4 s). The panel logs `[DevPanel] warp -> …` and `[DevPanel] now in …`, so a headless run proves the warp from stdout — no pixel inspection needed. `--dev-panel-keys` advances one token per frame, so build in an explicit `WAIT*N` after ENTER for the fade and map load to finish before the capture. To exercise the panel the way a user does, use the mouse/resize tokens (`CLICK:x:y`, `DBLCLICK:x:y`, `MOVE:x:y`, `WHEEL:n`, `RESIZE:w:h`) — a plain click selects, a double click warps. The capture is paired with a `state:` line (focus, rows, matches, selection, hover, filter, text fields) because a BMP cannot show whether a field is empty. Warps are refused (loudly, on the panel) while a battle is running or a non-overworld scene owns `callback1`.
- The panel's destination table is built **before** `AgbMain` starts, in `Platform_DevPanelInit()`. Do not move that build into the frame loop: it reads `gMapGroups` and the map layouts, which a live map load rewrites (`gMapHeader`) and `InitMap` mutates.
- Past-the-rival iteration: `./firered-native --post-rival --boot-test 200` reaches Oak's Lab with the starter and the first rival battle already done in ~3.5 s as well. It shares the `--skip-intro` save setup, so the two flags are ordered/interchangeable, but `--post-rival` suppresses the bedroom NES replay (UP at 60–65, A at 90–95) that `--boot-test` runs under `--skip-intro` — that interaction does not exist in the lab, and replaying it there would just be dropped input.
- Missing-symbol workflow: `make -f Makefile.native` then extract `grep -oE '"_[A-Za-z0-9_]+"'` from linker output; find real definitions with `grep -rln "SymbolName" src/*.c`; add that file to ENGINE_SRCS (or PREPROC_SRCS if it has `INCBIN`/`_()`) and DELETE the stub version from `stubs.c`. Battle-engine symbols now come from the real sources; four stub files remain: `src/platform/battle_engine_stubs.c` keeps the non-battle scene substitutes and tripwires, `src/platform/battle_peripheral_stubs.c` holds the ~119 peripherals a wild battle never reaches (safari, Poké Dude tutorial, Teachy TV, Union Room, Easy Chat, field moves), and `src/platform/stubs.c` holds the link layer plus the save-file entry points. (The M4A half of `stubs.c` is gone: `src/m4a.c`, `src/m4a_tables.c`, `src/m4a_driver.c` and `src/sound.c` are the real implementations.)
- **Auditing a stub's signature, before you trust it (fix #57).** A stub TU and the engine TU that calls it never share a header, so a wrong prototype compiles and links silently in both — the compiler cannot warn, and the linker takes whichever definition wins. The cheapest reliable check is to make the compiler arbitrate: add the corresponding `include/**.h` to each stub file and rebuild. Every disagreement becomes a hard `conflicting types` / `redefinition with a different type` error, which enumerates the whole backlog in one pass — including **wrong-typed data**, which no function-signature audit can find (`const u8 gPokedexEntries[] = { 0 }` against `const struct PokedexEntry[]` cost 48 bytes per entry, and `u8 gMaxFlashLevel = 0` against `const s32 = 4` silently disabled cave flash). When a source can be linked for real, prefer that to correcting a stub: `src/field_specials.c` alone retired 20 hand-written mirrors. Watch for two link-time traps while doing this — a source that needs `src/m4a.c` cannot link yet (its `asm("swi 0x2A")` is GBA-only), and `__stack_chk_guard` in `nm -u` output is libc, not a missing symbol.
- **Save-backed checks live in `tests/save_backed.c`** (tagged `engine fixture:bedroom`). `gSaveBlock1Ptr`/`gSaveBlock2Ptr` are NULL until `SetSaveBlocksPointers`, so Pokédex and coin checks need a booted engine — the runner's fixture supplies one and each test forks from it. Do not move these back into the game binary: they used to run from `AgbMain` on every launch.
- **Same-second mtimes: a restored source can be invisible to `make`.** GNU Make 3.81 (the system `make` on macOS, and there is no newer one unless Homebrew's `gmake` is installed) compares mtimes at **one-second granularity** — verified directly: with the object at t=1000.0 and the source at t=1000.5, `make -q` reports up to date; at t=1000.9 vs t=1001.4 it correctly rebuilds. So any source edit — or restore — that lands in the *same second* as the object's build is not seen, and `make` silently links the object compiled from the old source.
  The way this bites is proving a test fails: mutate a source to break the behaviour, rebuild, watch the test fail, then **restore the source with `cp` and run a bare `make` — and the test keeps failing against the object built from the broken source.** That is a phantom failure, not a flaky test, and it is easy to misread as "the fix didn't work".
  **`touch` is NOT a reliable fix** — if the touch lands in the same second as the object's build, `make` still cannot tell (proved: a same-second touch after a same-second `cp` restore did not rebuild; a touch in a later second did). This is why the `FPS_OVERLAY` advice to `touch src/platform/sdl2.c` is wrong in principle and only works in practice because it is run long after the object was built.
  **The reliable fix is to delete the object**, and there is a target for it:
  ```bash
  make -f Makefile.native clean-tests     # removes the engine + test objects, rebuilds, relinks
  ```
  Use it after any `cp`/`git checkout` restore of a source file, and after `git stash pop`. `rm -rf build` works too but rebuilds every asset as well.

- **A green incremental build is not proof the tree compiles.** Header dependencies are now tracked (fix #22), but object files still do not depend on `CFLAGS` or on the source-list variables, so `make` can reuse objects that a changed Makefile should have rebuilt. Removing `string_util.c`'s preproc rule produced a clean-looking incremental build while the stale object was still in place; only `rm -rf build && make -f Makefile.native` exposed it. Verify build-system changes from scratch. A missing preproc source fails loudly (`_(x)`/`__(x)`/`INCBIN` are undefined outside the IDE/Cygwin guard in `global.h`), never silently.
- Field-effect data regeneration: `python3 tools/gen_field_effect_data.py` rewrites `src/data/field_effects/{scripts_data.h,ptr_table.c}`. Deterministic, tracked in git, and NOT regenerated automatically — re-run it after editing `data/field_effect_scripts.s`, after adding a field-effect `.c` to `Makefile.native`, or after deleting a stub that shadowed a native. It prints the effects it left NULL and why (the native is not linked).
- Battle data regeneration: `python3 tools/gen_battle_data.py` rewrites `src/data/battle/{battle_data,anim_data,ai_data}.h` and `ptr_table.c`. Output is deterministic (verified by hash), and the generated files ARE tracked in git, matching the `src/data/maps_data.h` convention. `Makefile.native` does not regenerate them automatically; re-run the tool after editing `data/battle_scripts_*.s` or the readers in `battle_script_commands.c`.
- Sound data regeneration: `python3 tools/gen_sound_data.py` rewrites `src/data/sound/{voice_data.h,song_data.h,sound_data.c}` (all tracked). Deterministic, and NOT regenerated automatically — re-run it after editing `sound/voice_groups.inc`, `sound/keysplit_tables.inc`, `sound/cry_tables.inc`, `sound/song_table.inc`, any `sound/songs/midi/*.mid` (or its `midi.cfg` options), or after teaching it a new voice macro. It needs `tools/mid2agb` built. It prints a one-line summary (voicegroups, keysplits, waves, samples, songs, cry entries, pointer-table entries) and warns on stderr for a voice argument it cannot classify.
- Sample `.bin` assets are build products, not sources: `sound/direct_sound_samples/**/*.wav` are tracked and `Makefile.native`'s wav2agb rules build the `.bin` blobs on demand (cries DPCM-compressed and padded to 4 bytes, voices uncompressed). `tools/list_incbin_assets.py` resolves a `.bin` from the `.wav` beside it, so they are covered by the asset stamp and not reported as unbuildable.
- Map data regeneration: `python3 tools/gen_map_data.py` rewrites `src/data/{maps_data.h,layouts_data.h}` (both tracked). Not regenerated automatically — re-run it after adding a script label to `NATIVE_SCRIPT_ROOTS`, after editing any `data/maps/*/scripts.inc`, or after teaching the compiler a new script command. A scene whose closure fails to compile is reported on stderr as `gen_map_data: <label> left stubbed: <reason>` and keeps its `sDummyScript` fallback, so a silent no-op interaction means "run the generator and read stderr", not "the generator was never run".
- Driving a scripted battle: message boxes and many controller states wait on `JOY_NEW(A_BUTTON|B_BUTTON)`, which needs a fresh press *edge*. A held key never satisfies it - inject a press/release cadence (e.g. 4 frames on, 4 off) through `REG_KEYINPUT` in `WaitForVBlank`.
- **Sound "stuttering, cutting in and out", with a buzz that starts partway through? Count exact-zero runs in the dumped output before suspecting the resampler or the queue.** Fix #75 presented exactly that way: 25.8% of the frames were digital silence in 1,581 separate dropouts, and the repetition rate of the drops (~375 Hz) was the buzz. Distinguish producer from consumer first — instrument `Platform_SubmitAudioFrame` and count frames where the *engine's* `gSoundInfo.pcmBuffer` is entirely zero, versus frames the SDL callback emitted because its queue starved. Only the second is a queue/buffering problem; the first means the mixer is producing silence, and the place to look is the per-channel `statusFlags`/`envelopeVolume`/`gateTime` each vblank. In this case the channels were flipping ON → OFF every few vblanks, which points at whatever installs a note (`ply_note`) rather than at the mixer loop.
- **Sound "choppy", "buzzy", or "worse than an emulator"? Measure the resampler, do not adjust buffer sizes.** The engine's 13,379 Hz PCM meets the device at `src/platform/audio_resample.c`, and a zero-order hold there is audibly wrong (2.27% of energy lands above the source Nyquist). Dump what the SDL callback actually plays (`gOut`-style `fwrite` in `AudioCallback`) and compute (a) the energy above the source Nyquist and (b) the sample-jump mean at vblank boundaries against a **random-interior control** -- a boundary figure alone looks alarming even at chance. Also count output frames over 500 vblanks: a resampler that does not carry its sub-sample position runs ~0.04% fast, which sounds like a slow pitch rise and is invisible to any waveform check. **Do not skip the dropout count above first** — a real stutter makes the seam statistics meaningless, and this is the order the two defects in #74/#75 were actually found in.
- **Sound present but "missing instruments" or "thin"? Check whether the PSG half is being synthesised at all.** The GBA has two sound sources; the DirectSound FIFOs are the PCM mix in `gSoundInfo.pcmBuffer`, and the four PSG channels exist only as `NR10`..`NR52` register writes that `src/platform/psg.c` must turn back into samples. Measure rather than listen: disable the `Platform_PsgMix` call in `src/m4a_driver.c`'s `SoundMain`, keep the `gOut` dump in the SDL callback (see the audio section), and diff the two runs — that is how the 32.9%-of-energy gap in fix #73 was found. A `--boot-test` diff of `gSoundInfo.pcmBuffer` will *not* show it if the DirectSound mix already saturates the byte.
- **A CGB voice sounds buzzy or out of tune? The pulse is a sampled square, not a band-limited one.** Fixes #76/#77: sampling a pulse at 13,379 Hz folds its harmonics *below* the source Nyquist as inharmonic tones (a 1872 Hz note put its 5th/7th harmonics at 4017 and 272 Hz), and nothing downstream can separate them. `src/platform/psg.c` now uses a 64-point band-limited table per duty setting. Test for it by measuring the specific folding bins, not by listening, and set `PSG_DAC_SCALE` by the PSG-to-DirectSound ratio *inside the mixer* (mean |sample| of each), never by how loud one channel should be.
- **A CGB channel's level is not in its NRx2 register.** NRx2's high nibble is the envelope's initial volume (0 for a note attacking from silence) and its low nibble drives the hardware envelope unit; the running level is `CgbChannel.envelopeVolume` in the engine's struct. Reading NRx2 gives a permanent zero, which looks exactly like "the registers are never read". Panning is the other way round: NR51 is live and `CgbChannel.pan` is the engine's copy.
- **No sound, but `[Audio] opened ... audio device` printed?** The device is not the signal path. Grep the handoff's name across the whole tree — `grep -rn "Platform_SubmitAudioFrame" src include tests` — and confirm it appears somewhere other than its declaration (`include/platform/platform.h`), its definition (`src/platform/sdl2.c`) and the test stub (`tests/platform_host.c`). It must appear in `src/main.c`'s `VBlankIntr`, immediately after `m4aSoundMain()`. This was missing for the whole first pass at the sound port and nothing else noticed: the driver mixed, the song sequenced, the device opened, and the game was silent (fix #71).
- **When you test a producer/consumer pair, assert the consumer.** `tests/sound.c` had three tests reading `gSoundInfo.pcmBuffer` that all passed with the handoff deleted. The seam is where the bugs are: `tests/platform_host.c` is the harness's consumer and now records what it receives (`gHarnessAudioSubmits`/`gHarnessAudioMagnitude`), so a test can assert the handoff rather than the mix. It is the same reasoning as asserting rendered pixels rather than engine sprite state — see the PPU note above.
- A `SIGSEGV`/`SIGBUS` backtrace handler is installed in `src/platform/main.c` (`CrashHandler`) — crashes print a symbolized stack trace.
- **Input ordering (only relevant if you hand-roll input):** the loop is `ReadKeys()` … `WaitForVBlank()`, and `Platform_UpdateInput()` (called from `WaitForVBlank`) overwrites `REG_KEYINPUT` with the real SDL state every frame, so writing the register from inside `WaitForVBlank` by hand is one frame late and immediately clobbered. The harness already does this correctly (`tests/input.c`); use `Test_Press`/`Test_Hold` rather than writing `REG_KEYINPUT` yourself. If you ever do write it by hand, confirm with `gMain.heldKeys`, not `REG_KEYINPUT`.
- **The `--skip-intro` NES interaction leaves the field locked (game binary only).** Frames 60–95 hold UP then A to replay the bedroom NES, which opens a dialogue script with `LockPlayerFieldControls()` and nothing dismisses it headless — so a *`--boot-test` run* reports `locked=1`, `moving=0` and takes no steps for the rest of the run. This does not affect `firered-tests`: `gEngineMaxFrames` is 0 there, so that scripted input is never injected and the fixture starts idle. When writing a test, note that warping *onto* a wild-encounter tile locks the field via `CheckStandardWildEncounter()` — start on a clear tile beside the grass and step in.
- **Verifying a field effect:** `FieldEffectActiveListContains(FLDEFF_X)` is the precise check for "the effect started", and it is short-lived (the tall-grass rustle self-stops after its animation), so assert it in the frame window while it is alive. Compare OBJ VRAM against the source asset to prove the graphics loaded, and diff a capture with the effect against one without (`Test_RenderFrame()` + `Test_RegionDiffers`) to prove it renders — the tall-grass rustle showed up as an exact 16px-wide pixel span. `tests/field_effects.c` pins the script table; the pixel half belongs in a test too, not a probe.
- `compile_flags.txt` at repo root configures clangd with `-DPORTABLE -DMODERN=1 -DFIRERED`; keep it in sync with `Makefile.native` CFLAGS.

## 5. Build & Run Instructions

### Headless launches — REQUIRED for every launch the assistant performs

**Prefix every test, smoke, boot or dev-tool invocation with `SDL_VIDEODRIVER=dummy`, unless the user explicitly instructs otherwise** (e.g. "show me the window", "launch it visibly", "I want to watch"). This is a hard rule, not a preference. The project owner is using the machine while you work, and a real SDL video driver orders the game window front-centre on creation, steals keyboard focus, and bounces the Dock icon — repeatedly, for the whole run (a full `--boot-test 9300` is ~156 s of engine time).

```bash
SDL_VIDEODRIVER=dummy ./firered-native --skip-intro --boot-test 200
```

The dummy driver makes SDL skip window creation entirely, so nothing can appear on the owner's screen. **Nothing diagnostic is lost.** Verified against the checked-in binary:

| Capability | Under `SDL_VIDEODRIVER=dummy` |
|---|---|
| Screenshots (`engine_boot_output.bmp`, `ppu_test_output.bmp`) | Real, not blank (240×160, 45 distinct colours on the bedroom capture); `sha256` reproducible across runs |
| Frame pacing | Intact — 120 frames in 2.07 s wall vs the 2.009 s engine target |
| `REG_KEYINPUT` injection (`--boot-test` auto-input, and the harness's `Test_Press`) | Unaffected — it bypasses SDL input by construction |
| `./firered-tests` (all suites, including the engine fixtures) | Unaffected — and it needs no SDL at all, so this variable is irrelevant to it |
| `--dev-panel` + `--dev-panel-keys` | Still works: the panel creates its own renderer and falls back to software (1,317 destinations, panel BMP and `state:` line verified under the dummy driver) |
| Exit codes and stdout reporting | Unaffected |

Why it costs nothing: `Platform_SaveScreenshot()` (`src/platform/sdl2.c`) wraps `sFramebuffer` — the 240×160 BGR555 array `PPU_RenderFrame()` fills — in an `SDL_Surface` and calls `SDL_SaveBMP`, never touching the window. The window is used only by `Platform_PresentFrame()` (texture upload + `SDL_RenderPresent`), and `Platform_Init()` already falls back to `SDL_CreateRenderer(sWindow, -1, 0)` when accelerated rendering is unavailable. `WaitForFrameDeadline()` uses `SDL_GetPerformanceCounter()` (`mach_absolute_time`), which the dummy driver does not affect.

Interactive play is the one case where a visible window is the point — **never launch it that way unless the user asked for it.**

Every command example in this file and in §3's Debugging Tips is written **without** the prefix for legibility. That does not weaken the rule: add `SDL_VIDEODRIVER=dummy` to all of them when *you* run them.

Prerequisites (installed via Homebrew):
```bash
brew install sdl2 libpng pkgconf
```

### Build native binary:
```bash
make -f Makefile.native
```
A fresh `git clone` builds with no extra setup. The build generates everything it consumes: the C tools (`tools/gbagfx`, `tools/preproc`, `tools/mapjson`, `tools/jsonproc`) are built on demand — a `tools` target runs a sub-make for them before any asset recipe, because pret's rule files use pattern rules that leave no place to attach them as a prerequisite — and the constants headers pret derives from JSON (`include/constants/map_groups.h`, `layouts.h`, `map_event_ids.h`, `region_map_sections.h`, `heal_locations.h` and the `src/data/*` ones) are regenerated from the same tools and inputs pret uses. `assets` is a prerequisite of every object (order-only), since each object `INCBIN`s generated graphics during preprocessing.

The asset list is derived, not hand-maintained: `tools/list_incbin_assets.py` scans `src/` for `INCBIN` targets, drops the ones git tracks, and resolves the rest against the build's own rules — including assets assembled from other assets, like the `graphics/unused/obi1.4bpp` `cat` chain. Targets it cannot resolve are reported on stderr as `[assets] no build rule for ...; skipping`. `python3 tools/list_incbin_assets.py --list-targets` prints the concrete targets the rule files name.

### Release build — no development FPS overlay:
```bash
rm -f build/native/platform/sdl2.o && make -f Makefile.native FPS_OVERLAY=0
```
`FPS_OVERLAY` defaults to `1` (`Makefile.native` line ~7; it appends `-DFPS_OVERLAY` to `CFLAGS`). `src/platform/sdl2.c` guards the FPS counters, glyph table, and both draw calls with `#ifdef FPS_OVERLAY`, so a `FPS_OVERLAY=0` binary contains no overlay code. **The stale `sdl2.o` must be deleted first**: object files do not depend on `CFLAGS`, so `make` would otherwise keep the previously compiled overlay (same trap as fix #22). `rm -f build/native/platform/sdl2.o` is the reliable form — do not substitute `touch src/platform/sdl2.c`, which is only reliable when the touch lands in a later second than the object's build (see the same-second trap below). `-B` also works but rebuilds everything, assets included.

Verified: with `FPS_OVERLAY=0` the compile line carries no `-DFPS_OVERLAY`, `nm build/native/platform/sdl2.o` reports zero `fps` symbols, and the running window shows an overlay-free bedroom; the default build shows `FPS 60`.

### Build and run the unit tests:
```bash
make -f Makefile.native tests     # builds ./firered-tests
./firered-tests                   # run all
./firered-tests --list            # names, tags and fixture cost
./firered-tests --filter npc      # name or tag substring, repeatable
./firered-tests --explain         # print observations, never fail (probe mode)
./firered-tests --slow            # also run tests tagged `slow`
./firered-tests --timeout 5       # per-test hang timeout, seconds (default 30)
./firered-tests --selftest        # boot the engine through the harness and stop
```

`firered-tests` links the **same engine objects** as the game, minus three SDL-facing translation units (`src/platform/{sdl2,dev_panel,main}.c`) which the harness replaces. There is no SDL in the test binary at all: no window, no renderer, no `SDL_VIDEODRIVER=dummy` needed. Excluding `sdl2.o` also removes the display clock, so tests run the engine as fast as the CPU allows rather than pacing to 59.7275 Hz — a fixture boot takes ~0.4 s instead of ~3.5 s.

Nothing in `src/` is test-specific and nothing in `src/` includes the harness. The seam is `Platform_RenderAndPresent`, which the engine already calls exactly once per frame; the harness's implementation is the frame tick that hands control back to the test body (`tests/frame.c`).

Isolation is one process per test: the runner forks per test, the child boots its fixture and runs exactly one test. A crash (this port has had several — the door-animation SEGV, the trainer-card SEGV, the BAG list-menu segfault) is attributed to the one test that caused it and the run continues; a hang is caught by `alarm()`; engine state never leaks between tests.

### Writing a test
No list to edit: add a `.c` file under `tests/`, write a function with
`FIRERED_TEST(...)` on it, and it registers itself. The build finds the file and
the runner finds the test inside the binary (self-registration into a Mach-O
section, `tests/registry.h`).

The three arguments are the **name** (what `--filter` matches and what output
shows; prefix it with the area, e.g. `daisy/...`), the **tags** (see below), and
a **unique C function name**:

```c
#include "registry.h"

FIRERED_TEST("bios/div", "bios pure", bios_div)
{
    TEST_EQ(Div(100, 5), 20);
    TEST_EQ(Div(123, 0), 0);   // divide-by-zero is defined as 0, not a trap
}
```

**Tags decide whether the engine is booted before the body runs:**

| Tag | Meaning |
|---|---|
| *(none)* | Pure test: no boot, reads static data or calls a function directly. Runs in microseconds. |
| `engine` | Boot the game before this test. **Required** for anything that touches live engine state. |
| `fixture:bedroom` | Boot into the player's bedroom on a fresh save (`--skip-intro`). |
| `fixture:lab` | Boot into Oak's Lab with the starter received and the first rival battle won (`--post-rival`). |
| `fixture:dex` | ...and Oak's parcel already delivered, so the save owns the Pokédex (`--post-parcel`). |
| `slow` | Excluded from the default run; include with `--slow`. For a test that must drive a whole flow. |

A test that calls `Test_RunFrames`/`Test_WarpTo`/`Test_Press*` **must** carry
`engine` (and a `fixture:`). Forgetting it fails loudly with that message rather
than passing silently against an engine that was never started.

An engine test reads as straight-line code, because the harness gives control
back to the test body between frames:

```c
FIRERED_TEST("daisy/gives the town map after the parcel", "engine fixture:lab npc:daisy",
             daisy_town_map)
{
    // The gift branch is gated on the parcel having been delivered, which the lab
    // fixture does not arrange: write the precondition the way a real playthrough
    // leaves it, then test only the interaction.
    Test_SetVar(VAR_MAP_SCENE_PALLET_TOWN_RIVALS_HOUSE, 1);

    Test_WarpTo(MAP_GROUP(MAP_PALLET_TOWN_RIVALS_HOUSE),
                MAP_NUM(MAP_PALLET_TOWN_RIVALS_HOUSE), 5, 5);
    Test_RunFramesToWarp();

    Test_Press(DPAD_UP);              // turn to face Daisy
    Test_RunFrames(3);
    Test_PressUntilIdle(A_BUTTON, 900);

    TEST_TRUE(Test_HasItem(ITEM_TOWN_MAP, 1));
    TEST_EQ(Test_Var(VAR_MAP_SCENE_PALLET_TOWN_RIVALS_HOUSE), 2);
    TEST_EQ(Test_Flag(FLAG_HIDE_TOWN_MAP), TRUE);
}
```

**The vocabulary** (all declared in `tests/registry.h`):

- *Drive the engine* — `Test_RunFrames(n)`, `Test_RunUntilIdle(max)`,
  `Test_WarpTo(group, num, x, y)`, `Test_RunFramesToWarp()`.
- *Input* — `Test_Press(button)` (one press/release cycle), `Test_PressRepeated`,
  `Test_Hold(button, frames)`, `Test_ReleaseAll()`,
  `Test_PressUntilIdle(button, max)` (the "advance dialogue / open this menu"
  primitive: it presses first, then waits for the engine to go idle again).
  Buttons are the engine's masks: `A_BUTTON`, `B_BUTTON`, `DPAD_UP`, …
- *Observe* — `Test_Var`, `Test_Flag`, `Test_HasItem`, `Test_Money`,
  `Test_LastTalked`, `Test_FieldLocked`, `Test_MapGroup`, `Test_MapNum`,
  `Test_PlayerX/Y`, `Test_PlayerFacing`, `Test_InOverworld`, `Test_PartyCount`,
  `Test_PartySpecies`, `Test_PartyLevel`, `Test_StringVar4()` (dialogue,
  charmap-decoded).
- *Scripts* — `Test_ScriptStartsWith(script, SCR_CMD_*)`,
  `Test_ScriptFindOpcode`, `Test_ScriptPtrAt`, `Test_ScriptContains`,
  `Test_ScriptDump`. Opcode names come from `tests/script_ops.h`.
- *Pixels* — `Test_RenderFrame()` then `Test_DistinctColors`,
  `Test_RegionIsUniform`, `Test_RegionDiffers`.
- *Assert* — `TEST_EQ`, `TEST_NE`, `TEST_GE`, `TEST_TRUE`, `TEST_FALSE`,
  `TEST_STR_EQ`, `TEST_MEM_EQ`, `TEST_PTR_EQ`, `TEST_PTR_NOT_NULL`, `TEST_FAIL`.
  Every failure prints both operand values, e.g. `got 13 vs 6`, not just "failed".

### Every behaviour change gets a test, and it stays as a regression test
**This is the default workflow, and it replaces probing.** When you implement a
feature or fix a bug, write a test for the behaviour in the same change. Do not
write a throwaway probe in `src/platform/main.c` and delete it afterwards — that
workflow left 14 documented "verified with a temporary probe (since removed)"
entries in this file, each one a reproduction that had to be performed again by
hand the next time the area changed.

Concretely:

1. Write the test **before** the fix where you can, and confirm it **fails** —
   a test that passes both before and after proves nothing. `git stash` the fix
   to check, or revert the generated data as the historical defect did.
   **After restoring the source, run `make -f Makefile.native clean-tests`, never
   a bare `make`.** Deleting the objects is the only reliable way to get the
   restored source compiled; see the same-second trap below.
2. Fix the bug / finish the feature.
3. Confirm the test now **passes**, and that the rest of the suite still does.
4. **Keep it.** It is now the regression test for that behaviour.
5. If the change was a portability fix of the kind in the numbered list above,
   say in the fix's write-up which test pins it.

`--explain` is what makes this practical: it prints what every assertion observed
(`tests/engine.c:22: Test_MapGroup() == ... (4, 4)`) and never fails, so the same
file serves as the reproduction while you are investigating and as the assertion
once it is fixed. Run it, read the values, and only then decide what the expected
value is — that is how the coordinate-space confusion behind `Test_PlayerX` and
the charmap ambiguities were found, rather than guessed at.

A test is only worth keeping if a plausible bug would make it fail. Delete a test
that pins implementation detail (wiring, byte offsets in generated data, a
default value, a source string) — such a test breaks on legitimate refactors and
teaches people to re-pin numbers instead of reading the failure.

### What to assert
Assert **observable behaviour**, not implementation. The API is deliberately the
engine's own: the helpers above read live engine state through the real headers,
so a failure means the game is wrong, not that a helper drifted.

Prefer the thing the player or the script observes: `Test_HasItem` after a gift,
`Test_StringVar4()` after talking, `Test_Var` for a scene's progress,
`Test_FieldLocked` for whether an interaction holds the field. For scripts, assert
what the script *does* — `Test_ScriptStartsWith(script, SCR_CMD_LOCK)` — rather
than that a particular byte sits at a particular offset; asserting raw operand
bytes breaks on legitimate generator changes and trains people to re-pin numbers
instead of reading the failure.

Rendering is available on demand for behaviour that exists only as pixels
(`Test_RenderFrame()` then `Test_DistinctColors`/`Test_RegionDiffers` into the
harness's own buffer), but engine state is almost always the better thing to
assert. Prefer differential checks — capture with the effect, capture without,
diff the region — over golden pixel hashes: fixes #51 and #52 each changed
legitimate compositor output, and a golden hash would have failed for the right
reason and been regenerated away.

### Regenerating test inputs
`tests/script_ops.h` (named opcodes) is generated: `python3 tools/gen_script_ops.py`, or `make -f Makefile.native script-ops`. It reads the engine's dispatch table (`src/data/script_cmd_table.h`), whose entry order *is* the opcode numbering, and the build regenerates it when that table changes. Like `src/data/maps_data.h` and `src/data/battle/*.h`, the output is tracked in git.

## 7. Git & Commit Guidelines
